Building With AI

How to Orchestrate AI to Build Real Software — and Know Exactly Where to Distrust It

Primer 3 · The one that’s actually your edge

Why this primer is different

The first two primers taught you how software moves and what it’s made of. This one is about making it — and specifically, making it the way the highest-leverage builders work in 2026: by directing AI, not by hand-typing every line.

Here’s the honest thesis. A product-minded person who can orchestrate AI to build, and who knows precisely where AI gets things wrong, is a more valuable profile than a junior engineer who writes everything by hand. That’s not hype — it’s the actual shape of the advantage available to you. This document hands you the terrain, the starter kit, and the judgement. The fluency you’ll build yourself, by hitting walls and climbing over them.

This is not a syllabus. It’s a map and a kit. Everyone reading it will take a different route, on their own repo, building their own thing in the same broad domain. That divergence is the point, not a bug. Go fast if you’re fast; go deep if you’re grounded; go sideways if you’ve got a better idea. Compare notes later.

1 · The Mental Shift: From Writing Code to Directing It

Start here, because everything downstream depends on getting this reframe right. For decades, building software meant a human typing every line. AI changes the unit of work: you now describe intent in precise language, the AI drafts the code, and your job shifts from author to director and editor. You decide what to build, you steer how it’s built, and — this is the part that matters most — you judge whether what came back is actually correct.

This plays directly to your strengths. As a PM you already think in requirements, edge cases, and trade-offs. That’s exactly the skill set that makes someone good at directing AI: the bottleneck is no longer “can you write the syntax,” it’s “can you specify clearly and verify rigorously.” Both are things you’re already wired for.

The director’s three jobs

Specify — describe what you want precisely enough that a capable but literal-minded collaborator could build it. Vague in, vague out.

Steer — review the draft, push back, ask for changes, break the work into reviewable pieces. You’re in a loop, not placing a single order.

Verify — the one job you can never delegate. The AI is confident whether it’s right or wrong. You are the check on that confidence. The rest of this primer is mostly about doing this job well.

There’s a failure mode to name immediately, because it’s the one that catches everyone. AI makes it intoxicatingly easy to produce code that looks finished — it runs, it’s formatted, it’s plausible. The gap between “looks done” and “is correct” is where every AI-assisted disaster lives. A junior hand-writing code at least struggles visibly when they don’t understand something. AI hides that struggle behind fluent output. Your entire value-add as a Product Engineer using AI is refusing to be lulled by fluency.

The standard you’re held to

At FundsIndia, every line you ship — whether you typed it or prompted it — goes through real-engineer review. That gate doesn’t care whether a human or an AI wrote it; it cares whether you understand it and can defend it. “The AI wrote it” is never an answer in a review. If you can’t explain why a line is there, it’s not ready. This is the right pressure, and it’s exactly what turns AI-assisted speed into AI-assisted competence.

2 · The Stack: Your Starter Kit, Part by Part

To build a real, full-stack app — something with a frontend, a backend, a database, user accounts, and a public URL — you need a handful of pieces working together. This section names each one, says what job it does, and points you at the specific tool we recommend starting with. Recall the three-layer anatomy from Primer 2 (frontend / backend / database); this is that skeleton, made concrete.

A recommended stack, not the only stack

What follows is a proven starting point — the fast path, chosen because it’s beginner-friendly, well-documented, has generous free tiers, and is the stack we can most readily unblock you on. It is explicitly not the one true way. If you have reason to pick a different database, host, or framework — or you just want to learn by swimming in unfamiliar water — do it. The concepts transfer. Part of the exercise is developing the judgement to make these choices yourself.

The pieces and what each one does

Git version control

Tracks every change to your code, locally, with full history. The thing that makes editing safe (see Primer 1, §2). You’ll use it constantly, mostly through a few simple commands.

GitHub code home

The hosted home for your Git repo — the online copy, where your code lives, where you open PRs, and what your deploy host reads from. Your project’s public-facing source of truth.

github.com

Supabase backend + database + auth

The fast path’s secret weapon. One service that gives you a real Postgres (SQL) database, user authentication, file storage, and auto-generated APIs — the things that would otherwise take weeks to wire up. Generous free tier.

supabase.com

A deploy host puts it online

Takes your code from GitHub and runs it at a real URL the world can reach. Vercel is ideal for frontend-heavy apps; Railway is great for backends and services (you’ve used it). Both have free tiers and deploy automatically when you push.

vercel.com / railway.app

Claude your build partner

The AI you direct to write, explain, debug, and refactor code — via the chat interface, via Claude Code in your terminal, or via the API when you want Claude inside your app. This is the engine of the whole approach.

claude.ai / docs.claude.com

Your editor where you work

Where you read and edit code. VS Code is the default choice and integrates with Claude Code. This is your cockpit.

code.visualstudio.com

How the pieces fit together

A request’s journey, end to end: a user opens your app’s URL (served by your deploy host), which loads your frontend. They log in — Supabase handles the authentication. They do something that needs data — your backend asks Supabase’s database, which answers. You built all of it by directing Claude, you saved your work with Git, pushed it to GitHub, and the deploy host noticed the push and put the new version live. That’s the whole loop. Every app you admire is an elaboration of it.

Two primitives that trip everyone up

Environment variables and the .env file

Your app needs secrets — the password to your database, your API keys — but those must never be written directly into your code (because your code goes to GitHub, where secrets would be exposed). The solution is environment variables: secrets live in a special file called .env that stays on your machine and is deliberately kept out of Git. Your code reads from it by name, like SUPABASE_KEY, without the actual value ever appearing in the code.

# .env  — this file stays local, never committed to Git
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=eyJhbGc...your-secret-key...
ANTHROPIC_API_KEY=sk-ant-...your-claude-key...

The number-one beginner mistake

Accidentally committing secrets to GitHub. It happens constantly, and for a financial app it’s a serious incident — a leaked database key can mean leaked customer data. The safeguard is a file called .gitignore that tells Git to ignore .env entirely. Verify this is set up before your first push, and if you ever do leak a key, treat it as compromised and rotate (regenerate) it immediately — deleting the commit is not enough, because the history remembers. When you direct Claude to set up a project, explicitly ask it to add .env to .gitignore.

API keys: how your app proves it’s allowed

An API key is a long secret string that identifies your app to a service (Supabase, Claude, a payment gateway) and proves it’s authorised to make requests — the app-level equivalent of the authentication you read about in Primer 2, §4. You generate keys in each service’s dashboard, store them in .env, and your code presents them on every request. Treat them like passwords: one per service, never shared, never in screenshots, rotate if exposed.

3 · Setup: From Blank Machine to Live App

This is the path from nothing to a deployed app you built by directing AI. Don’t treat it as gospel steps to copy — treat it as the shape of the journey, so you recognise where you are when you’re in it. Crucially: you don’t do most of this by hand. You direct Claude to do it and you verify each result. The whole point is to learn by building, with AI as the one doing the typing and you doing the thinking.

The healthiest way to use this section

Open Claude in one window and your terminal/editor in another. Go through this rung by rung, and at each step ask Claude to do it and explain what it’s doing and why. “Walk me through initialising a Git repo for a new project and explain each command” teaches you ten times more than copying commands. When something breaks — and it will — paste the exact error to Claude and ask it to explain the cause before fixing. The errors are the curriculum.

  1. Set up your machine

    Install your editor (VS Code), Git, and a runtime (Node.js is the common one). Ask Claude: “I’m on [your OS] starting from scratch — walk me through installing VS Code, Git, and Node, checking each worked.” Starting from near-zero on a terminal is normal; that’s exactly the position to learn from.

  2. Create accounts

    Sign up for GitHub, Supabase, and a deploy host (Vercel or Railway), and get API access to Claude. All have free tiers. Keep the dashboards open — you’ll generate keys from them.

  3. Start a project and put it under Git

    Create a project folder, initialise Git, and make your first commit. Direct Claude through it and have it explain git init, git add, git commit as you go — these are the Primer 1 concepts made real under your own hands.

  4. Connect it to GitHub

    Create a repo on GitHub and push your local project to it. Now your code has an online home. Confirm you can see your files on github.com — that’s your source of truth, live.

  5. Wire up Supabase

    Create a Supabase project, grab its URL and key into your .env file, and connect your app. Ask Claude to scaffold a simple data table (say, a list of savings goals) and the code to read and write it. You now have a real database behind your app.

  6. Add authentication

    Turn on Supabase Auth so users can sign up and log in. Direct Claude to add a login screen and protect a page behind it. This is AuthN/AuthZ (Primer 2, §4) made tangible — and a core flow for anything FundsIndia-adjacent.

  7. Deploy it

    Connect your GitHub repo to Vercel or Railway. It builds and serves your app at a real URL. Every future git push redeploys automatically — that’s the CI/CD loop from Primer 1, §4, running for free on your own project.

  8. Now iterate

    You have a live, full-stack, authenticated app. Everything from here is adding features, fixing bugs, and refining — the actual work of product engineering, which the rest of this primer and the task ladder are about.

What you’ll have learned by surviving this

Notice what just happened: by building one real app, you touched version control, repos, databases, schemas, auth, environment variables, API keys, deployment, and CI/CD — every primitive from the first two primers, in context, with your own hands. This is why building beats reading. The concepts that felt abstract on the page become things you’ve done. That’s the transition, in miniature.

4 · How to Actually Build With AI

There’s a craft to directing AI well, and the gap between someone who’s good at it and someone who isn’t is enormous — same tool, wildly different results. The difference is almost entirely in how you specify, scope, and steer. Here’s what actually works.

Specify like you’re writing a spec, because you are

The quality of what you get back is capped by the quality of what you ask for. “Make a login page” gets you something generic and probably wrong for your needs. A good prompt carries the same things a good PRD does: the goal, the constraints, the edge cases, the context of what already exists, and what “done” looks like.

Weak prompt vs. strong prompt

Weak: “Add a goal tracker.”

Strong: “Add a savings-goal feature to this app. A goal has a name, a target amount in rupees, a target date, and a current saved amount. Users should see their goals as cards showing percent complete. They can add, edit, and delete goals. Use the existing Supabase setup and match the styling of the dashboard page. Handle the empty state (no goals yet) and validate that target amount is positive. Show me the data model first so I can check it before you build the UI.”

The second one isn’t longer for its own sake — every clause removes a wrong guess the AI would otherwise make. The last sentence is the highest-leverage habit in this whole document: make AI show you the plan before the code.

Scope into reviewable pieces

The instinct to ask for the whole feature at once is the instinct to fight. Large AI-generated chunks are hard to review, hard to debug, and hard to understand — and remember, you have to defend every line at the review gate. Work the way good engineers work (Primer 1, §3): small, focused changes you can actually read. “Show me the data model.” Check it. “Now the function to save a goal.” Check it. “Now the UI.” Each piece is small enough to genuinely understand. This is slower in the moment and far faster overall, because you’re not debugging a 500-line mystery.

Steer, don’t restart

When the AI gets something wrong, the beginner move is to scrap it and re-prompt from scratch. The better move is to steer: “This is close, but the date validation allows past dates — fix just that.” You’re in a conversation with a capable collaborator who can take correction. Treat it like a code review you’re giving: specific, targeted feedback, one thing at a time.

Knowing which surface fits a task is itself a product-engineering judgement: don’t reach for an API call when a one-off chat would do, and don’t hand-build something Claude Code could do across your whole repo in one pass.

5 · Reading & Distrusting AI-Generated Code

This is the heart of the document — the skill that separates a Product Engineer using AI from someone generating liabilities at speed. AI writes plausible code. Plausible is not the same as correct, and the failure modes are specific and learnable. Your job is to develop a trained suspicion: not paranoia that rejects everything, but calibrated doubt aimed at the places AI reliably gets things wrong.

The cardinal rule

Never ship code you can’t explain. If the AI produced something and you don’t understand why a line is there, you have two honest options: ask it to explain until you do, or don’t use it. “It works and I’m not sure why” is a time bomb — and it will not survive the review gate. Understanding is non-negotiable; it’s the entire difference between directing AI and being a conduit for it.

Where AI reliably gets things wrong

These are the high-suspicion zones — the places to slow down and verify every time, because AI’s confidence is flattest exactly where the risk is highest:

Failure modeWhat it looks likeWhy it’s dangerous for FundsIndia
Plausible-but-wrong logicCode that runs and looks right but computes the wrong thing — an interest formula off by a compounding period, a rounding that loses paise.On a wealth platform this is real money and a regulatory exposure. The output looks fine; only domain knowledge or a test catches it.
Made-up APIs & librariesCalling a function or package that doesn’t exist, or using an outdated way of doing something. AI sometimes confidently invents plausible-sounding names.Wastes time, and the “fix” the AI suggests can send you down a rabbit hole. Verify libraries are real and current.
Missing edge casesHappy path works; empty states, zero values, negative numbers, huge numbers, concurrent actions, and errors are unhandled.Edge cases in finance are where the incidents and the angry customers are. This is exactly where your PM instinct for edge cases is the asset.
Security gapsSecrets in code, missing authorization checks, unvalidated user input, data exposed that shouldn’t be.PII and money. A missing “can this user see this account?” check is a breach, not a bug.
Silent assumptionsThe AI assumed something about your data, your setup, or your intent that isn’t true, and built on it without flagging.The error compounds — everything built on a wrong assumption inherits it.

A practical review pass for AI code

Before you accept a chunk of AI-generated code — and well before it reaches a human reviewer — run it through this. It becomes second nature fast.

  1. Read every line and narrate it

    Can you say out loud what each line does? Where you can’t, ask the AI to explain that specific line. Gaps in your narration are gaps in your understanding.

  2. Hunt the edge cases

    What happens with no data? Zero? A negative? A huge number? Two users at once? A network failure mid-action? Ask explicitly: “what edge cases does this miss?” — then verify the answer rather than trusting it.

  3. Check the money math by hand

    For anything financial, compute one example yourself and confirm the code agrees. This single habit catches the most dangerous class of error.

  4. Look for secrets and missing auth

    Any keys hard-coded? Any action that should check “is this user allowed?” but doesn’t? These are the security basics that matter most.

  5. Verify the unfamiliar bits are real

    Any library or function you don’t recognise — confirm it actually exists and is the current way to do it. A quick check saves a long detour.

  6. Make it prove itself with a test

    Ask the AI to write a test (Primer 1, §4 — and the dedicated testing primer) that demonstrates the code does the right thing, especially on the edge cases. A passing test you understand is real evidence; “it ran once” is not.

Use AI to check AI

A powerful move: paste the AI’s own code into a fresh conversation and ask “review this critically — what’s wrong, what edge cases are missing, what would a senior engineer flag?” A clean context is often sharper than the one that wrote the code. This doesn’t replace your judgement or the human review gate — but it’s a strong first pass, and it doubles as a way to learn what good reviewers look for.

6 · AI Features: Evals, Cost, Latency, Failure

Everything so far is about using AI to build software. This section is about building software that contains AI — a feature that calls Claude at runtime, like a portfolio-explainer chatbot or a document summariser. This is a different discipline with its own concerns, and it’s where a lot of FundsIndia’s AI roadmap will actually live. Orientation depth here; you’ll go deeper when you build one for real.

The four things that are different about AI features

Evals: how you know it’s good

Normal code is deterministic — same input, same output, and a test passes or fails cleanly. AI output varies and is judged on quality, not just correctness, so “does it work?” becomes “how good is it, across many cases?” An eval is a structured way to measure that: a set of representative inputs, and a way of scoring the outputs (exact-match where possible, or a rubric, or even another AI grading against criteria). Without evals you’re flying blind — you change a prompt, something feels better, but you can’t tell if you quietly broke ten other cases. If you’ve ever tuned a filter or a ranking by eyeballing a few examples and hoping the rest improved too, evals are what make that rigorous instead of vibes.

The PM-native skill hiding here

Evals are essentially “define success metrics and test against representative cases” — which is product thinking. Deciding what good looks like for an AI feature, and how to measure it, is squarely your job and plays to your strengths. The engineering is in the harness; the judgement is in the rubric.

Cost: every call is metered

Each API call to an AI model costs money, priced by the amount of text in and out (measured in “tokens” — roughly, fragments of words). It’s small per call and very real at scale. A feature that calls the model on every keystroke, or stuffs huge documents into every request, can run up a serious bill. Connect this to the resources thinking from Primer 2, §6: AI features have a unit economics that you, as the product person, should be able to reason about — cost per user, per action, per month.

Latency: AI is slow compared to normal code

A database query returns in milliseconds; an AI model might take several seconds to respond, especially for longer outputs. That’s an eternity in user-experience terms. It shapes design: you show streaming responses (text appearing as it’s generated) so it feels alive, you set expectations with loading states, and you don’t put a slow AI call in the middle of a flow that needs to be instant. Latency is a product decision as much as a technical one.

Failure: AI features fail differently

Normal code fails loudly and predictably — it errors, you catch it. AI can fail softly: it returns something confident and wrong, or off-tone, or subtly unhelpful, with no error at all. So building AI features means designing for graceful degradation (what shows if the model is down or slow?), guardrails (what stops it saying something it shouldn’t, especially in a regulated financial context?), and a way for users to recover when the AI gets it wrong. The question is never just “does it work when it works” — it’s “what happens when it doesn’t.”

The regulated-context caveat

In wealth management, an AI feature that gives something resembling financial advice, or states a number as fact, carries real regulatory and trust weight. “The AI said it” is not a defence. Any user-facing AI at FundsIndia needs human-defined guardrails on what it will and won’t say, clear framing of what it is, and careful handling anywhere it touches advice, returns, or specific numbers. Treat this as a first-class design constraint, not a finishing touch — and a place to pull in compliance early.

7 · Forge Your Own Path

Here’s where this document deliberately stops holding your hand. You have the mental shift, the stack, the setup path, the craft of directing AI, the discipline of distrusting it, and an orientation to building AI features. That’s genuinely enough to start. Everything else — the fluency, the taste, the speed — comes from building things and hitting walls, not from reading further.

The invitation

Build something real in the wealth/investing/goal-planning space — the domain you’re about to work in — on your own repo, your own way. A goal planner. A portfolio visualiser. A SIP calculator with a twist. A fund explorer. The domain is shared so the concepts rhyme with FundsIndia and you can compare notes; the implementation is entirely yours. There is no hymn sheet here, on purpose.

Go your own way, genuinely

If you’re fast, race ahead and build something ambitious. If you’re grounded, go slow and deeply understand every piece before moving on. If a different stack calls to you, take it — the concepts transfer. If you’ve got a question that the docs don’t answer, chase it down; the best questions here are the ones that teach the person who asked them, and sometimes the person they ask. Divergence is the design, not a deviation from it.

How to know you’re getting somewhere

You don’t need a certificate. You’ll know you’re building real fluency when: you can take a feature idea and direct it into existence without getting stuck on setup; you catch the AI’s mistakes before they cost you; you can read code you didn’t write and explain it; you reach for a test to prove something rather than hoping; and — the real bar — an engineer reviews your work and treats you as a credible peer. That respect, earned and not granted, is the gate. It isn’t timed. Some of you will reach it quickly; one of you arrived already having earned it elsewhere. Both are fine. The only wrong pace is not building.

Where this sits in the suite

This primer is the engine; the others are the manual. When you hit version control, lean on Primer 1. When you’re reasoning about a database or auth, Primer 2. When you’re staring at code you didn’t write, or trying to test something, or wondering why your deployed app is misbehaving — the depth primers on reading unfamiliar code, testing, and observability are written for exactly those walls. And the task ladder sequences the whole climb. Read none of them cover-to-cover up front; summon each when the wall appears. That just-in-time habit is itself how engineers actually learn.

A standing offer

The deepest value in this whole exercise isn’t in any document — it’s in the questions you’ll generate by building. Bring the ones that stump you. The genuinely hard questions are where the learning compounds, for you and for whoever you ask. Now close this and go build something.
