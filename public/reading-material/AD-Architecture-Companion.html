Diagram 3.1 - Catalog and reference data

L1 expansion of the Catalog bounded context. Commodity ingestion at the base, proprietary enrichment in the middle, lifecycle and operational surfaces on top.

Diagram 3.2 - Catalog sequence diagrams

3A. Daily NAV refresh and downstream propagation

After AMC NAV publication, primary source ingestion, reconciliation against secondary source, enrichment recomputation, event emission, and downstream consumer reactions.

3B. Scheme merger corporate action

Two schemes consolidate: source scheme is delisted, target scheme absorbs holdings at an allocation ratio. Catalog applies the merger forward while preserving historical NAVs, Portfolio retroactively adjusts holdings, Ledger writes adjustment postings, and customers are notified.

Diagram 4.1 - Order and execution core

L1 expansion of the Order Execution bounded context. Order intake, pre-trade validation, routing by asset class, execution rails, post-trade handling, and the legacy bridge during migration.

Diagram 4.2 - Order execution sequence diagrams

4A. Lumpsum MF purchase, happy path

Customer places a lumpsum buy on an MF scheme well before cut-off. All gates pass, BSE StAR routes the order, RTA confirms allotment, ledger posts, holdings update.

4B. SIP instalment with mandate debit failure and retry

Scheduled SIP run. Mandate debit fails on first attempt (insufficient funds). Retry policy engages, customer notified to ensure funds, second retry succeeds three days later.

4C. Rail failover under primary outage

Customer places MF order during BSE StAR rail outage. Routing engine detects circuit breaker open, falls over to FP-mediated execution. Order succeeds via fallback. Recon engine tags the order for elevated post-trade verification due to non-primary rail.

Diagram 5.1 - Payments and mandates

L1 expansion of the Payments and Settlement bounded context. Payment orchestration, mandate lifecycle, pool account and settlement, refunds and reversals, and the legacy bridge during migration.

Diagram 5.2 - Payments and mandates sequence diagrams

5A. Mandate registration (NPCI eMandate, NACH)

Multi-day asynchronous flow. Customer authorises mandate, NPCI submits to sponsor bank, sponsor verifies and forwards to destination bank, destination bank approves, NPCI registry updated, mandate becomes active.

5B. Stuck-transaction recovery

Customer initiates a net-banking payment, payment gateway returns an ambiguous response (timeout). Platform does not know if the customer was charged. Recovery playbook queries PG status, confirms via NPCI lookup, resolves deterministically — no orphan debit.

5C. Daily pool-account settlement and reconciliation

End-of-day settlement cycle. Pool account inflows from PG settlements, outflows to AMC for buy orders, AMC inflows for redemptions, payouts to customer accounts. Pool balance reconciled against ledger expected balance. Breaks raised to operations.

Diagram 6.1 - Ledger

L1 expansion of the Ledger bounded context. Double-entry, bitemporal, immutable. Every financial state change recorded canonically; every transition replayable from the spine.

Diagram 6.2 - Ledger sequence diagrams

6A. MF buy order — posting flow through to settlement

Order events flow into the ledger across the lifecycle. OrderSubmitted creates a pending posting, OrderAllotted resolves units, OrderSettled posts the cash leg. Each step is rule-driven, atomic, and bitemporal.

6B. Compensatory posting and correction

An erroneous original posting cannot be edited. A compensatory entry is posted with explicit linkage, net effect equals the correction. Maker-checker approval required, audit-traceable.

6C. End-of-day close and trial balance

NAV-day cut-off freezes same-day postings. Period operations compute closing balances, generate trial balance, hand off to recon and reporting. The daily heartbeat that keeps the ledger reliable.

Diagram 7.1 - Reconciliation

L1 expansion of the Reconciliation bounded context. Continuous comparison of platform truth against external (and legacy) sources, break management, ownership, attestation, and resolution.

Diagram 7.2 - Reconciliation sequence diagrams

7A. Daily transactional ledger vs RTA recon

The canonical daily cycle: pull RTA holdings, compare against ledger, identify matches, raise breaks for mismatches, route to owners.

7B. Break investigation and resolution

A break is picked up by ops, investigated, root cause identified, resolution path chosen (compensatory posting in Ledger), maker-checker approval, resolution applied, re-recon to confirm, attestation captured, break closed.

7C. Cohort migration recon: dual-run reconciliation cycle

During cohort migration, legacy state and new platform state are reconciled per customer per day. N consecutive days clean is a cutover gate. This is the workload that runs longest and matters most for migration success.

Diagram 8.1 - Event spine and data foundation

L1 expansion of the substrate that every other context depends on. Not a bounded context — infrastructure. Kafka-based event spine, lakehouse, feature store, vector store, lineage, PII enforcement, governance.

Diagram 8.2 - Event spine and data foundation sequences

8A. Event published and fanned out to multiple consumers

A producer context emits a domain event via the transactional outbox. CDC drains to Kafka. Multiple independent consumers — operational, analytical, ML — receive the same event with no producer awareness.

8B. Schema evolution: adding a field with backward compatibility

Producer wants to add a new field to OrderAllotted. Schema registry validates compatibility, new version published, old consumers continue working unchanged, new consumers can read the new field.

8C. Event replay: rebuilding a downstream consumer from scratch

The Portfolio read-model store is corrupted or needs to be rebuilt with a new schema. Reset consumer offset to beginning, replay all relevant events from the spine, idempotency ensures correctness.

Diagram 9.1 - Intelligence and AI layer

L1 expansion of the Intelligence and AI bounded context. Orchestration of LLM and classical ML across recommendations, advisory, conversation, and agentic action.

Diagram 9.2 - Intelligence and AI sequence diagrams

9A. RAG-grounded customer query

Customer asks: "Should I switch from Fund A to Fund B?" Orchestration assembles the prompt with customer state, retrieves grounding context, calls the foundation model, applies guardrails and tone, returns a grounded answer with citations.

9B. Agentic action with human-in-loop confirmation

Customer says: "Rebalance my portfolio to 70/30." Agent plans a multi-step action, queries portfolio and catalog, composes order drafts, requests explicit customer confirmation before any order is submitted.

9C. Daily recommendation refresh pipeline

Scheduled nightly job: features recomputed, ranking model scored for each customer, recommendations published, signals captured for future training. The classical-ML side of the layer that complements LLM-driven conversation.

Diagram 10.1 - Security, Fraud and AML

L1 view spanning two bounded contexts (Fraud and AML; Security as a cross-cutting plane). Three operational domains: security, fraud, AML. Distinct teams and cadences, shared substrate.

Diagram 10.2 - Security, Fraud and AML sequence diagrams

10A. Account takeover attempt detection and block

Fraudster attempts login from a new device using stolen credentials. Device intel and behavioural biometrics detect anomalies. Step-up auth fails. Account locked, customer notified out-of-band.

10B. Real-time AML transaction monitoring and STR filing

Customer exhibits a pattern of structured transactions over weeks. AML engine detects the pattern, opens a case, analyst investigates, supervisor signs off, STR filed to FIU-IND.

10C. Money mule ring detection across customer cohort

Cross-customer pattern detection: multiple new accounts receive inflows from common source and rapidly transfer out. Graph-based pattern analysis flags the ring. Accounts frozen pending investigation; FIU-IND notified.

Diagram 11.1 - Compliance, PII and DPDP

L1 view of the governance and regulatory bounded context. Counterpart to Diagram 10's operational security and AML plane: this diagram is policy, filings, data subject rights, retention, and audit. Cross-cutting linkages to consent ledger (Diagram 2), ledger (Diagram 6), and FIU-IND filing (Diagram 10) are referenced, not duplicated.

Diagram 11.2 - Compliance, PII and DPDP sequence diagrams

11A. Quarterly SEBI regulatory report compilation and filing

Filings calendar triggers compilation. Report engine pulls bitemporal data from ledger and identity contexts. Maker drafts, checker reviews, supervisor approves. Filing submitted to SEBI portal via adapter, acknowledgement reconciled.

11B. DPDP data subject access request (DSAR) fulfillment

Customer requests their data under DPDP Act. Consent state checked, cross-context aggregation pulls only purpose-scoped data, PII review and redaction applied to third-party data, packaged response delivered within statutory deadline.

11C. Right to erasure with statutory retention conflict

Customer requests erasure under DPDP. Retention engine identifies records SEBI mandates be retained. Conflict resolved: permitted data erased, retained data marked restricted-purpose (access limited to regulatory inspection only). Consent ledger updated, customer informed of partial fulfillment.

Diagram 12.1 - Legacy Bridge and Migration Substrate

L1 view of the legacy bridge and migration substrate. This is the operating model that makes every other L1's "Legacy bridge adapter" coherent. Migration is treated as a vendor-like, time-bound integration with a planned sunset, not a one-time conversion.

Diagram 12.2 - Legacy Bridge and Migration Substrate sequence diagrams

12A. Cohort cutover — preparing through post-cutover monitoring

A cohort moves through the state machine: preparing → dual-write → dual-read validation → cutover → post-cutover monitoring. Each gate is recon-clean; routing flips per-customer; legacy stays warm.

12B. In-flight order continuity across cutover boundary

An MF purchase order is placed minutes before the cutover gate fires for that cohort. State machine moves mid-flight. Order continues on the platform that owned it at submission, completes there, and the resulting holdings appear correctly on the post-cutover new platform without duplicates.

12C. Post-cutover rollback triggered by monitoring breach

Post-cutover monitoring window detects an SLA breach. Rollback decision is taken. Cohort is routed back to legacy. New-platform writes during the post-cutover window are propagated back to legacy via reverse-flow. Rollback completes, root cause investigation begins.
