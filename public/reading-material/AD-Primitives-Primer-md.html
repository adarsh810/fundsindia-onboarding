1 · The Anatomy of an Application

Almost every product you’ll work on is built from the same three layers. Hold this skeleton in mind; the rest of the primer fills in each bone.

Layer What it is FundsIndia example
Frontend What the user sees and touches — the screens, buttons, charts. Runs on the user’s device (browser or phone). The portfolio dashboard you tap through in the app.
Backend The brain behind the screens — the logic, rules, and calculations. Runs on servers you control. The engine that computes your returns, applies fees, and checks rules.
Database The long-term memory — where all the data is stored permanently and safely. The record of every user, holding, transaction, and goal.

How they talk: the API The frontend and backend talk to each other through an API (Application Programming Interface) — a strict, agreed-upon menu of requests one piece of software can make to another. The frontend says “give me this user’s holdings”; the backend, via the API, replies with the data. An API is a contract: “if you ask me in exactly this format, I promise to answer in exactly that format.” Most integration work — between your own systems, or with partners like mutual-fund registrars or payment gateways — is API work. PM lens When you scope a feature, it helps to ask: which layers does this touch? A copy change is frontend-only (cheap, fast). A new calculation is backend. A new kind of data to remember is a database change (often the most consequential, because data structure is hard to change later). “Which layers?” is one of the highest-leverage questions a PM can ask early.

2 · Databases: The System’s Memory

A database is an organised, durable store of information designed so the software can write, find, and update data quickly and reliably — even with millions of records and thousands of simultaneous users. It is the single most important primitive in most products, because the data usually outlives every other part of the system.

The two great families

SQL (Relational) NoSQL (Non-relational)
Shape Tables with rows and columns — like a set of strict, interlinked spreadsheets. Flexible — documents, key-value pairs, graphs. Less rigid structure.
Best when Data is structured and relationships matter (users, accounts, transactions). Data is huge, fast-changing, or loosely structured (logs, sessions, catalogs).
Examples PostgreSQL, MySQL, Oracle, SQL Server. MongoDB, DynamoDB, Cassandra, Redis.
Trade-off Extremely reliable and consistent; structure is rigid to change. Flexible and massively scalable; you give up some guarantees.

Why finance loves SQL For a wealth platform, SQL is usually the backbone, because money demands consistency: a transaction must either fully happen or not at all — never half-recorded. SQL databases are built around exactly this guarantee (the “ACID” properties, below). NoSQL often shows up alongside it for the high-volume, less-critical stuff like activity logs or caching.

Key concepts you’ll hear

Term Plain meaning
Table A spreadsheet-like collection of one kind of thing (e.g. a “Users” table).
Row / Record One entry in a table (one user, one transaction).
Column / Field One attribute every row has (email, balance, created-date).
Primary key The unique ID that identifies each row unmistakably (like a customer ID).
Foreign key A link from a row in one table to a row in another (this transaction belongs to that user).
Index A lookup shortcut that makes searches fast — like a book’s index. Speeds reads; costs a little on writes.
Query A request to the database (“find all users in Bengaluru with balance > 1 Cr”), written in SQL.
Schema The blueprint: what tables exist, their columns, and how they relate.
Migration A controlled, version-tracked change to the schema (adding a column, a new table).
ACID The four reliability guarantees (Atomicity, Consistency, Isolation, Durability) that keep data trustworthy.

The word “migration” — why engineers get careful Changing the structure of a live database (a migration) is delicate surgery, because the data is already there and the system is running. Adding an optional column is usually safe; renaming or removing one, or changing a type, can break things or require careful staged rollout. When an engineer says a feature “needs a migration,” treat it as a signal of higher care and coordination — not necessarily more effort, but more risk to plan around. PM lens Data structure is the most expensive thing to get wrong, because it’s the hardest to change once real data has accumulated. When you spec a feature, think early about what new data we need to remember and how it relates to what we already store. A fifteen-minute data-model conversation at spec time routinely saves weeks later. This is also where your strong IC instincts genuinely shine.

3 · Files, Directories & How Code Is Organised

Underneath the polish, a software project is a tree of folders and files — the same folders-and-files idea as your laptop, just more disciplined. A directory is a folder; the file system is the overall tree. Understanding this demystifies a lot of what you see when you peek into a repo.

The vocabulary

Term Plain meaning
Directory / folder A container that holds files and other folders.
Path The “address” of a file, e.g. /src/components/Dashboard.js — read left to right as folders nested inside folders.
Root The top of the tree — the project’s home folder, where everything branches from.
File extension The bit after the dot (.js, .py, .json) signalling the file’s type.
Config file A settings file (often .json, .yaml, or .env) that controls how the app behaves without changing core code.

A typical project, annotated

You don’t need to memorise this, but recognising the shape removes the intimidation factor. A backend project often looks roughly like:

project-root/ src/ — the actual source code tests/ — the automated tests docs/ — documentation package.json — the project’s ID card: name, version, dependencies README.md — the “start here” explainer for humans .env — secret settings (passwords, keys) — never shared publicly

Dependencies & packages Almost no code is written from scratch. Engineers stand on dependencies — pre-built packages of code (also called libraries) that solve common problems, pulled in from public registries (npm for JavaScript, PyPI for Python). The package.json file lists exactly which ones, and which versions. This is powerful (don’t reinvent the wheel) but also a supply-chain risk: a bug or vulnerability in a popular package affects everyone who uses it, which is why those security scans in CI matter.

4 · Authentication & Authorization: Who You Are vs. What You Can Do

These two words sound alike and are constantly confused, so we’ll nail them precisely — they’re among the most important primitives in any product that touches money or personal data.

Authentication (AuthN) Authorization (AuthZ)
Question it answers “Who are you? Prove it.” “Now that I know who you are — what are you allowed to do?”
Real-world analogy Showing your passport at the airport. Your boarding pass deciding which lounge and seat you can access.
Mechanisms Passwords, OTPs, biometrics, “log in with Google.” Roles & permissions (admin vs. customer vs. support agent).
Fails like… “Wrong password” — we can’t confirm it’s you. “Access denied” — we know it’s you, but you’re not permitted.

The order matters Authentication always comes first: the system establishes who you are, then authorization decides what that identity may do. A support agent and a customer might both be perfectly authenticated, but they’re authorized very differently — the agent can see many accounts, the customer only their own.

Concepts you’ll meet

Term Plain meaning
Session The period you stay logged in after authenticating, so you don’t re-enter your password on every click.
Token / JWT A tamper-proof digital wristband the server gives you after login, which your app shows on each request to prove it’s still you.
OAuth The standard behind “log in with Google/Apple” — lets you authenticate via a trusted third party without sharing your password.
MFA / 2FA Multi-factor auth: requiring a second proof (an OTP, an authenticator app) on top of the password.
Role-based access (RBAC) Granting permissions by role (admin, agent, customer) rather than person-by-person.
Encryption Scrambling data so only authorised parties can read it — in transit (HTTPS) and at rest (in the database).

PM lens In a regulated wealth business, authorization is a product and compliance surface, not just plumbing. “Who can see this? Who can approve that? What can a support agent do on a customer’s behalf, and is it logged?” are product decisions with real regulatory weight (think RIA vs. MFD boundaries, maker-checker approvals, audit trails). Getting the permission model right is squarely PM territory — and a place where sloppiness becomes a compliance finding.

5 · State & State Machines

State is simply “the current situation” — the snapshot of all the relevant facts at this moment. Your shopping cart has state (what’s in it). A KYC application has state (submitted? approved? rejected?). Much of software is the careful management of state as it changes over time.

State machines: taming the chaos of “what can happen next”

A state machine is a precise map of (a) all the states a thing can be in, and (b) the allowed transitions between them. It’s a powerful tool because it forces you to think through every situation explicitly — and to forbid the nonsensical ones.

A worked example: an investment order Placed → Confirmed → Processing → Completed …with branch transitions like Placed → Cancelled or Processing → Failed. The state machine encodes the rules: an order can go from Placed to Cancelled, but not from Completed back to Placed. By drawing this explicitly, the team prevents impossible, money-losing situations — like cancelling an order that’s already settled. You can think of a state machine as a board game: each square is a state, and the rules say which squares you can move to from where. Illegal moves are simply not on the board.

PM lens State machines are one of the most PM-friendly engineering tools that exist — you can sketch one on a whiteboard with no code at all. For any feature involving status — KYC, onboarding, order processing, support tickets, withdrawals — drawing the states and the allowed transitions yourself, and crucially asking “what happens if it’s in state X and Y occurs?”, surfaces the edge cases that otherwise become production incidents. This is product-engineering thinking at its most accessible: a great state diagram is often a better spec than three pages of prose.

6 · Resources: Memory, Compute & Storage

Software runs on physical computers (usually rented from cloud providers like AWS, Google Cloud, or Azure). Those computers offer three fundamental resources. Conflating them is one of the most common sources of confusion, so here’s the clean mental model — a kitchen.

Resource What it is Kitchen analogy If you run low…
Compute (CPU) The processing power that does the actual work — calculations, logic. The chef’s hands and speed. Things get slow; work queues up.
Memory (RAM) Fast, temporary workspace for whatever the program is actively using right now. Wiped when the program stops. The countertop — ingredients out for the dish being cooked now. The app crashes or grinds to a halt.
Storage (Disk) Slow, permanent space where data is kept long-term, even when powered off. The fridge and pantry — everything kept for later. You literally can’t save new data.

The memory-vs-storage trap This is the distinction worth burning in. Memory (RAM) is fast but temporary and small — the active workspace, gone when the program stops. Storage (disk) is slower but permanent and large — the filing cabinet. “We ran out of memory” (a crash from too much active work) is a completely different problem from “we ran out of storage” (nowhere to save data). Engineers mean very different things by them; now so do you.

The cloud, in one paragraph

Instead of buying physical computers, companies rent these three resources on demand from cloud providers, paying for what they use. The huge advantage is elasticity — you can summon more compute during a market-open rush and release it afterwards. This is also why engineers talk about “scaling” and why cost and performance are linked: more resources cost more money, so efficiency has a direct line to the P&L.

Term Plain meaning
Server A computer (usually rented, in a data centre) that runs your backend and serves users.
Scaling up (vertical) Giving one server more power — a bigger machine.
Scaling out (horizontal) Adding more servers and splitting the load across them — usually the more robust approach.
Load balancer A traffic cop that spreads incoming requests evenly across multiple servers.
Cache A small, ultra-fast store of frequently-needed answers, so you don’t recompute or re-fetch them every time.
Latency The delay before a response — how long the user waits. Lower is better.
Throughput How much work the system handles per unit time — requests per second. Higher is better.

PM lens Resources are where product decisions meet the cloud bill. A feature that recomputes a heavy portfolio analysis on every screen load is a compute cost; one that keeps huge histories instantly queryable is a storage cost. You don’t need to size servers — but knowing that “this feature is compute-heavy” or “this will balloon our storage” lets you weigh value against running cost, and ask the right question: “what does this cost us to run at scale?”

7 · Data at Scale: Warehouses, Lakes & Pipelines

The database from Section 2 is built to run the live product — fast reads and writes for the app (this is called “operational” or “transactional” data). But when you want to analyse data — trends, dashboards, ML models, regulatory reporting — you need different tools, because crunching years of history is a very different job from serving one user’s next click.

Concept What it is The analogy
Database (operational) Stores live data to run the app. Optimised for speed on individual records. The busy front-of-house till.
Data Warehouse A separate store optimised for analysis across huge volumes. Structured, cleaned, query-ready. A well-organised library with everything catalogued.
Data Lake A vast pool holding raw data of every kind — structured and unstructured — cheaply, before it’s necessarily organised. A giant reservoir: everything flows in, organise it when you need it.
Pipeline / ETL The automated plumbing that Extracts data, Transforms (cleans) it, and Loads it where it’s needed. The conveyor and sorting system moving water between pools.

Lake vs. warehouse, simply A warehouse is structured and cleaned up front — you decide the questions, then shape the data to answer them fast (great for finance dashboards and reporting). A lake stores everything raw and cheap, and you figure out structure later — great for data science and ML, where you don’t yet know all the questions. Many companies run both, and a modern blend is sometimes called a “lakehouse.” PM lens A crucial instinct: don’t run heavy analytics directly on the live product database. A giant report query can slow down the app for real customers. “Can we pull this from the warehouse instead of prod?” is exactly the kind of question that marks you as a product engineer rather than a passenger. For an IPO-track, regulated business, this separation also underpins clean, auditable reporting.
