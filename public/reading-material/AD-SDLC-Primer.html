The Software Delivery Lifecycle

A Field Guide to How Software Actually Gets Built, Tested, and Shipped

Primer 1 of 2 · For Product Managers becoming Product Engineers

Who this is for

You are a strong product person who understands technology at the surface — you can read a roadmap, talk to engineers, and reason about trade-offs. What you may not yet have is the mental model of the machine: where code lives, how it travels from a laptop to a customer, and what all those words in standup (PR, staging, rollback, CI) actually point to.

This primer closes that gap. By the end you should be able to sit in any engineering conversation and follow the plot — not as a spectator, but as someone who knows where the levers are.

0 · The One-Page Mental Model

Before the detail, hold this picture in your head. Everything else in this primer hangs off it.

Software is just text files (“code”) that a computer reads and acts on. A team of people edit those files. The hard part isn’t writing the text — it’s coordinating many people changing the same pile of text safely, and then moving a trustworthy copy of that text onto computers that customers actually touch, without breaking anything.

The Software Delivery Lifecycle (SDLC) is the disciplined answer to that coordination problem. It has two intertwined halves:

The two halves

1. The build loop (inner loop). A single engineer changes code on their own machine, runs it, sees if it works, fixes it, repeats. Fast, private, messy. Measured in seconds and minutes.

2. The delivery pipeline (outer loop). That change gets proposed to the team, reviewed, automatically tested, merged into the shared codebase, and then promoted step-by-step across environments until it reaches customers. Slower, public, governed. Measured in minutes to days.

A Product Engineer is someone who is fluent in both loops — who can not only describe the feature but open the code, make a change, and shepherd it safely through the pipeline. The rest of this document walks the whole journey, in order, the way a real change travels.

The journey of one change

Idea → write code locally → commit → push to a branch → open a Pull Request → automated checks (CI) → human review → merge → deploy to staging → deploy to production (CD) → monitor → (if broken) roll back.

Memorise this line. Every section below is one station on this track.

1 · Environments: The Parallel Worlds

An environment is a complete, self-contained copy of your software — the code plus the computers, database, and settings it runs on. The whole point of having several is to create safe places to make mistakes before customers can feel them.

Think of a stage play. You rehearse in an empty hall (nobody watching), then do a dress rehearsal with a small invited audience, then open on Broadway. Same script, escalating stakes. Environments are exactly this for software.

The standard ladder

EnvironmentWho uses itWhat it’s forIf it breaks…
LocalOne engineerThe code running on a single laptop. Private sandbox to build and experiment.Nobody notices.
Dev / IntegrationThe engineering teamFirst place everyone’s changes meet and run together.The team notices; customers don’t.
Staging / QA / Pre-prodQA, PMs, stakeholdersA near-perfect clone of production. Final dress rehearsal, demos, sign-off.Caught before customers — the whole point.
Production (“prod”)Real customersThe real thing. Live money, live data, live users.Customers feel it. This is the one that matters.

In plain English

When an engineer says “it works on staging”, they mean the change behaved correctly in the dress-rehearsal world. That is reassuring but not the same as “it works in production,” because production has real-world scale, real data, and real edge cases that staging only approximates. The gap between the two is where a lot of incidents live.

Why environments differ in subtle ways

Environments are supposed to be identical, but they rarely are 100%. Staging might have a smaller, anonymised copy of the database. Production has ten years of messy real customer records. A change that flies through staging can still trip over a weird record that only exists in prod. This is why “parity” — keeping environments as similar as possible — is a constant engineering concern, and why “it passed staging” is a green light, not a guarantee.

PM lens

Two practical habits. First, always ask “which environment is this in?” when someone shows you a working feature — a staging demo and a production release are very different commitments. Second, staging is your playground too: it’s where you should click through a feature and sign off before it goes live. Owning staging sign-off is one of the fastest ways a PM earns engineering trust.

2 · Repositories & Version Control: The Source of Truth

A repository (“repo”) is the folder that holds all of a project’s code, plus its entire history of every change ever made. It is the single source of truth for what the software is. Version control is the system — almost always a tool called Git — that records that history and lets many people edit safely.

The Google-Docs analogy (and where it breaks)

Version control is like the version history in Google Docs — it remembers every edit, who made it, and lets you roll back. But with two crucial upgrades: changes are batched into meaningful, labelled chunks (not saved keystroke-by-keystroke), and many people can work on separate copies in parallel and then merge their work together deliberately, rather than all typing into one live document.

The vocabulary you’ll actually hear

TermWhat it meansEveryday analogy
CommitA saved, labelled batch of changes with a message describing what changed and why.A labelled save point: “Fixed login button colour.”
BranchA personal parallel copy of the code where you can work without disturbing anyone else.Making a duplicate of the doc to draft in, before merging back.
Main / masterThe one official branch that represents the real, shippable product.The master copy of the manuscript.
MergeCombining the changes from one branch into another (usually back into main).Folding your edited draft back into the master copy.
Push / PullPush = upload your commits to the shared server. Pull = download everyone else’s.Sync up / sync down.
ConflictWhen two people changed the same line differently and Git needs a human to decide.Two editors rewrote the same sentence; someone must choose.
CloneMaking your own full local copy of a repo to start working.Downloading the whole project folder, history and all.

Why branches are the key idea

The branch is the single most important concept here. Imagine twenty engineers all editing the live product at once — chaos. Instead, each person creates a branch off main, does their work in isolation, and only merges back when it’s reviewed and tested. Main stays clean and shippable at all times; the messy work-in-progress happens off to the side.

This is also why you’ll hear about a “feature branch” — a branch created specifically to build one feature or fix. Its name often maps directly to a ticket, e.g. feature/FI-1423-goal-calculator. When that work is done and merged, the branch is usually deleted; its history lives on inside main.

GitHub / GitLab / Bitbucket

Git is the underlying technology. GitHub, GitLab, and Bitbucket are the popular hosted homes for Git repos — websites where the shared copy lives and where reviews, discussions, and automation happen. When someone says “it’s on GitHub,” they mean the team’s shared, online source of truth lives there. (FundsIndia’s own repos live under accounts like github.com/…; ask your team which host you use.)

3 · Pull Requests & Code Review: The Quality Gate

A Pull Request (PR) — called a “Merge Request” on GitLab — is a formal proposal that says: “I’ve finished my work on this branch. Please review it and, if you approve, merge it into main.” It is the moment a private piece of work becomes a public, team-level decision.

A PR bundles together three things: the exact lines of code that changed (the “diff”), a description of what and why, and a conversation thread where reviewers comment, ask questions, and request changes. Nothing reaches main without passing through this gate.

What a “diff” looks like

A diff shows only what changed, line by line. Removed lines are marked in red with a −, added lines in green with a +. A reviewer doesn’t re-read the whole program — they read just the delta, which is why small PRs get reviewed fast and giant ones languish.

Why code review exists

Code review is the engineering equivalent of a second pair of eyes on a contract before you sign it. It catches bugs, spreads knowledge across the team (so no single person is the only one who understands a piece of code), enforces consistency, and creates a written record of why a decision was made. A good review culture is one of the strongest signals of a healthy engineering org.

The anatomy of a healthy PR

  1. Small and focused. One logical change. A PR that does five unrelated things is hard to review and risky to merge.
  2. Clearly described. What changed, why, how it was tested, and a link to the ticket it closes.
  3. Green checks. All the automated tests (CI — next section) have passed.
  4. At least one approval. A teammate has read it and clicked “Approve.” Many teams require this before merge is even possible.
  5. Conversations resolved. Every comment has been addressed or discussed.

PM lens

You will increasingly be on PRs — sometimes opening small ones yourself, often reviewing or commenting on copy, behaviour, and edge cases. You don’t need to judge code elegance; you can catch “this doesn’t match the spec,” “what happens if the user has no goals yet?”, or “the empty state text is wrong.” That product-level review on a PR is enormously valuable and very welcome. Also: PR size is a leading indicator of delivery health — a team drowning in 2,000-line PRs is a team that will ship slowly and break things.

4 · CI/CD: The Automated Assembly Line

CI/CD is the automation that turns the manual, error-prone job of testing and shipping code into a reliable assembly line. It’s two linked ideas: Continuous Integration (CI) and Continuous Delivery/Deployment (CD). This is the beating heart of modern delivery, so we’ll take it slowly.

CI — Continuous Integration: “does this change break anything?”

Every time someone opens or updates a PR, a robot springs into action. It takes the proposed code, assembles it, and runs a battery of automated checks — all without a human lifting a finger. If anything fails, the PR is flagged with a red X and merge is blocked.

What does CI actually run? Typically:

  • Build / compile. Does the code even assemble into a runnable program? (For some languages this catches whole classes of errors instantly.)
  • Automated tests. Hundreds or thousands of tiny scripted checks that each verify “given this input, the code produces the right output.” More on test types below.
  • Linting & formatting. Style and consistency checks — the automated grammar-and-spellcheck of code.
  • Security & dependency scans. Looks for known vulnerabilities in the code or the third-party libraries it relies on.

Why “continuous”

The name comes from the old, painful alternative. Teams used to integrate everyone’s work together rarely — once a month — and it was agony, because months of divergent changes all collided at once (“merge hell”). The fix was to integrate continuously: small changes, merged often, each automatically verified. Lots of tiny safe steps instead of rare terrifying leaps.

CD — Continuous Delivery & Deployment: “get it to customers, safely and automatically”

Once a change passes CI and is merged into main, CD takes over: it automatically packages the new version and promotes it through the environment ladder. There’s a subtle but important distinction in the two D’s:

TermWhat’s automatedThe human’s role
Continuous DeliveryEverything up to production. The release is built, tested, and parked — ready to ship at the push of a button.A human decides the moment to release to customers.
Continuous DeploymentEverything, including the release to production. If it passes all checks, it goes live with no human gate.None — the pipeline ships automatically. Requires deep trust in the tests.

Plain English

Think of CI/CD as a car factory conveyor belt with automatic safety inspectors. CI is the inspectors checking each part as it’s added (“does this bolt fit? is it cracked?”). CD is the belt that carries the finished, inspected car out to the showroom. The whole appeal is that quality is checked constantly and automatically, so problems are caught in minutes by a robot rather than days later by an angry customer.

A quick word on test types (so the jargon lands)

Test typeChecks…Analogy
Unit testOne tiny piece of logic in isolation (e.g. “does the interest calculator return the right number?”).Testing a single Lego brick.
Integration testWhether several pieces work correctly together.Testing that two Lego sections click together.
End-to-end (E2E) testA full user journey through the real app, like a robot clicking through screens.Testing the finished Lego model by playing with it.

PM lens

“Good test coverage” isn’t engineering vanity — it’s delivery speed insurance. Teams with strong automated tests ship faster and more confidently, because the robots catch regressions before customers do. When you hear “we need to add tests first,” that’s usually an investment in future velocity, not a delay tactic. A useful PM question: “is this covered by tests, or are we relying on manual checking?”

5 · Deployment, Release & Rollback

Deployment is the act of putting a new version of the code onto the computers that run an environment. Releasing is the act of making that new version visible to users. These often happen together but — importantly — they can be separated, which is the foundation of safe shipping.

Strategies for shipping without holding your breath

StrategyHow it worksWhy it’s safer
Feature flagCode is deployed but hidden behind an on/off switch. You flip it on for users when ready — instantly, no redeploy.Decouples shipping code from releasing the feature. Bad feature? Flip it off in seconds.
Canary releaseRoll the new version out to a tiny slice of users (say 1%) first. Watch. If healthy, widen gradually.A problem hurts 1% of users, not 100%, and you catch it early.
Blue-greenRun two identical production setups. Switch traffic from old (“blue”) to new (“green”) all at once; switch back instantly if needed.Rollback is just flipping traffic back — near-instant recovery.

Rollback: the undo button

A rollback is reverting to the previous known-good version when a new release misbehaves. The single most important property of a healthy delivery system is that rollback is fast, boring, and rehearsed. When something breaks in production, the first instinct of a good team is usually not “debug it live” but “roll back first, investigate after” — stop the bleeding, then diagnose calmly.

PM lens

Feature flags are a product superpower, not just an engineering trick. They let you ship code dark, turn features on for internal users or beta cohorts, run A/B tests, and do staged rollouts — all without engineering redeploying. If your team uses flags well, you gain enormous control over when and to whom a feature appears. Ask whether new features are flag-gated; the answer shapes how much release risk you’re carrying.

6 · How It All Sequences: The Lifecycle End-to-End

Now zoom out. The stations you’ve learned — environments, repos, PRs, CI/CD, deploy — are the machinery. The SDLC is the repeating loop that runs that machinery, over and over, for every feature. Classically it’s drawn as these phases:

PhaseWhat happensWho leads / your role
1. PlanDecide what to build and why. Requirements, scope, success metrics.You. PM-owned.
2. DesignDecide how to build it. Architecture, data models, UX, technical approach.Eng + Design, with PM input
3. BuildWrite the code. The inner loop: code → commit → branch.Engineers
4. TestVerify it works. Automated (CI) + manual QA on staging.Eng + QA + PM sign-off
5. ReleaseShip it to customers via the CD pipeline, often behind flags.Eng, PM decides timing
6. Operate & MonitorWatch it in production. Logs, metrics, alerts, on-call.Eng + SRE, PM watches product metrics

Agile, in one breath

You’ll hear Agile, Scrum, sprints, Kanban. These aren’t a different lifecycle — they’re a rhythm for running it. Instead of doing all six phases once over a year (the old “waterfall” way), you run the whole loop in tiny slices every week or two (a “sprint”), shipping a small working increment each time. The machinery (repos, CI/CD) is what makes this rapid cadence possible — you can’t ship every two weeks by hand.

DevOps: the philosophy tying it together

DevOps is the cultural idea that the people who build software (Dev) and the people who run it in production (Ops) should be one collaborative team with shared ownership and heavy automation — rather than developers “throwing code over the wall” to a separate operations team. CI/CD is the toolkit; DevOps is the mindset. You’ll also hear SRE (Site Reliability Engineering) — a specific, Google-originated flavour of operations focused on keeping systems reliable using engineering discipline and clear reliability targets.

7 · The Standup Decoder

A quick-reference list of phrases you’ll hear daily, translated. Skim it now; come back to it whenever a sentence in standup loses you.

You hear…It means…
“I’ll push a fix”I’ll upload my code change to the shared repo.
“It’s blocked on review”The code is done but waiting for a teammate to approve the PR.
“CI is red / the build is broken”An automated check failed; nothing can merge until it’s fixed.
“Let’s ship it behind a flag”Deploy the code but keep the feature switched off until we choose to turn it on.
“It’s on staging”It’s in the dress-rehearsal environment, ready for you to test — not live yet.
“We need to roll back”Revert production to the previous working version because something broke.
“There’s a merge conflict”Two changes touched the same lines; a human must reconcile them.
“It’s a one-line change”Small code edit — but “small” doesn’t always mean “low-risk.” Ask about blast radius.
“Can you cut a release?”Package the current main into a versioned release ready to deploy.
“It works on my machine”It runs locally but might behave differently in a real environment (a classic warning sign).
“We’re paying down tech debt”Cleaning up earlier shortcuts so future work is faster and safer.
“This needs a migration”A change to the database’s structure that must be applied carefully (see Primer 2).

The takeaway

You don’t need to write production code to be a great Product Engineer — but you do need to know exactly where every conversation sits on the track from “idea” to “live.” When you can say “that’s merged but not released,” or “let’s canary it to 5% first,” or “is this behind a flag?”, you’ve stopped being a passenger on the delivery pipeline and started steering it.
