Framework reference

Change, Consistency and Propagation

This is how work moves and stays coherent across four mutually dependent layers, from product intent down to code and back up again. It is written to be read by both engineers and the product and design side, so the preamble below sets up the cast and the map before the detailed mechanics.

It deliberately stops at framework scope. Product architecture (DB engine, service topology, environment sizing) lives in the product project, not here.

Preamble: the cast and the map

Four layers of artifacts make up the system, each with one native owner and one home. The relationship between them is not a stack where the top dictates the bottom. It is a cycle: a change in any layer can ripple in either direction, and a constraint discovered in code can push back up to product as readily as a product decision pushes down to code.

1The four layers and who owns them

Every artifact has exactly one canonical home and one owner. Nothing is canonical in two places. What changes from a stack is that a link between two artifacts no longer implies one dictates the other; it only implies they must stay consistent.

Product and design layer. Strategy, PRDs, entities (the nouns of the domain), journeys (the verbs), and UI/UX journeys and design. Owned by PMs and designers, in Confluence and Figma. This is where intent originates most often, but not exclusively.

Technical design layer. Technical and UX-implementation design docs, owned by engineers and architects, authored in the repo and mirrored read-only into Confluence.

Code layer. Code, tests, infra-as-code, schema and migrations. Owned by engineers, in the repo.

Governance layer. Two registers, both in Confluence. The Open Decisions Register holds open questions routed to Business, Compliance, Legal, Product or Tech, each with an owner and a target date. The Drift Register holds the elements that are currently inconsistent across the locked docs; it is maintained by the integrity tooling and the Cowork loop, not hand-written.

The mirror. Technical design docs propagate one way, repo to Confluence, as a read-only reflection so product folks read them where they already work. That reflection is generated output, never hand-edited, and the mirrored pages carry a "synced automatically, do not edit" banner.

Design source. Figma is the dependable store for UI artifacts, with Claude Design earning its place over the two-month runway rather than being load-bearing on day one. In-repo design docs link to the design source; they never duplicate it.

2The dependency map

The map is the spine that makes consistency tractable across a circular graph. It is lightweight front-matter on each artifact. Two properties matter: links are typed, and links are navigable both ways.

Typed means a link records the nature of the relationship, not just that one exists: a design doc realises a PRD, code constrains a design doc, a change raises an open decision. Navigable both ways means the same link is read forward (what does this realise) and backward (what realises this), so a constraint found in code can be routed up to the PRD's owner, and a PRD change can be routed down to the design docs that realise it.

A technical design doc in the repo:

---
id: DD-042
title: Order Routing Service Design
status: active
realises:
  - { ref: CONF-PRD-123, store: confluence, version: 7 }   # the PRD it implements
  - { ref: CONF-JRN-018, store: confluence, version: 3 }   # the journey it serves
depends_on:
  - { ref: DD-031, store: repo }                            # an upstream design dep
raises:
  - { ref: ODR-009, store: confluence }                    # an open decision it triggered
sync_to_confluence: true
---

A test file carries coverage links, either as front-matter or, where the framework has no front-matter, a tagged annotation:

// @covers CONF-PRD-123, DD-042

The version stamp (version: 7) records the Confluence version each cross-store artifact was last reconciled against. A referenced PRD now at a higher version is the candidate signal that the link may have drifted. Because the link is typed, the tooling knows whose problem the drift is and which register to file it in.

3How consistency holds across a circular graph

You cannot topologically order a cycle, so the framework does not try to propagate changes in a fixed direction. Instead, any layer may originate a change, the tooling detects what is now inconsistent, and reconciliation is routed to the owning human in whichever direction the situation calls for. The two governance registers are the hub every cross-layer change passes through: questions go to the Open Decisions Register, inconsistencies to the Drift Register.

It runs in both directions in practice:

  • Downward. A PRD or UX journey changes. If it needs a call from Business, Compliance or Legal, that becomes an Open Decision. The design docs and code that realise it are marked in the Drift Register, and their owners reconcile them.
  • Upward. Engineering hits a code constraint. That raises an Open Decision, a trade-off or feature-phasing request, routed up to the PM or designer. They update the PRD or journey, which in turn marks the affected design docs and code as drifted, and the cycle closes.

So the doc you are reading is not a cascade. The engineering pipeline in section 4 is one path through the model, the path a code change takes, and it stays linear because the code path genuinely is. The circularity lives here, at the layer level, above the pipeline.

4The engineering change pipeline

This is the path a code change takes once it lands in the repo, whatever layer set it in motion.

4aAuthoring

Technical design docs, code, tests and infra go into the repo. During the ramp, eng holds the pen on in-repo design docs with PMs contributing through comments and PM-owned sections, graduating into repo authorship over the quarter.

4bPR-time gates (deterministic, GitHub Actions, no Claude)

  • Build, lint, and the unit and integration tests run.
  • The bespoke linter validates the map: front-matter is present and well-formed, typed links resolve, and changed artifacts carry the right @covers links.
  • A cross-store candidate check compares each referenced Confluence version to the stamped version. A newer source raises a warning, not a hard failure, because staleness is a judgment call, not a syntax error.
  • An ephemeral preview environment spins up so reviewers, PMs and design see a running thing, not just a diff.

Hard failures (broken build, failing tests, unresolved links, missing coverage) block the merge. Soft warnings (candidate drift) surface in the PR and are logged to the Drift Register for a human to judge.

4cMerge to main (deterministic propagation, no Claude)

On merge, the publisher action mirrors changed design docs to their read-only Confluence pages over the REST API, authenticating with an Atlassian API token in GitHub Secrets, and updates the version stamps. The deploy pipeline carries the build into non-prod automatically. Production stays behind the gate in section 6. No Claude runs in this path.

4dThe Cowork judgment loop

This is the only place Claude touches the documentation system. It runs as a scheduled Cowork flow (nightly) plus on-demand, reading the repo and reading and writing Confluence through the Atlassian MCP. It is detailed as its own workflow in section 5. It proposes; it never commits to a canonical doc on its own, and it runs on a dedicated always-on machine the steward owns, because Cowork scheduled tasks only run while that machine is awake and Claude Desktop is open.

4eHuman review and disposition

The steward and the relevant authors act on what the loop reports. Any fix, including ones Claude drafted, goes back through the normal PR flow and its gates. There is no side door that bypasses review.

5The Cowork consistency workflow

This is the engine that keeps the four layers coherent. It reads both stores, runs the consistency checks the deterministic layer cannot, writes its findings to the Drift Register and proposes reconciliations, then hands everything to a human.

The four checks map onto the layers: version control confirms git is coherent and the Confluence mirror matches the last-propagated design docs; the dependency check walks the typed map and flags drifted links via version mismatch; open decisions are reconciled in both directions (new questions captured into the register, resolved answers pushed into the artifacts they inform); semantic checks compare tech and UX design, and strategy against the PRDs beneath it. Everything the loop finds becomes a Drift Register entry with a proposed fix, and nothing lands in a canonical doc until a human approves it through the normal flow.

6The human gates

This is the governance spine, and the single most important part to write down so nobody relitigates it under deadline pressure.

The rule

Claude proposes, CD disposes. The following are human-gated and never automated or Claude-touched.

  • Production deploys. Require passing test gates and explicit review approval.
  • Applying migrations to production. Through the pipeline and human approval, never a live agent.
  • Any access to real customer data. No Claude tool, in any surface, reads or writes production data.

Approval authority sits with senior engineers and you. Secrets live in a cloud-native secrets manager, and production secrets are never exposed to Claude, to CI, or to any non-prod environment.

Residency, locked

The posture is the most conservative reading across the RBI, SEBI and AMFI axis, not the permissive DPDP baseline. Regulated customer data (KYC, transaction and financial PII) is stored and processed only in India, on an India-region cloud using MeitY-empanelled data centres, with backups, disaster recovery, logs and encryption keys also held in India. This treats the build as in-scope for the SEBI cloud framework and CSCRF regardless of the formal regulated-entity determination, which is the safe default while that determination is pending.

The compliance control that makes this work without constraining the toolchain is the data firewall in the flow: real regulated data never leaves the production estate, and Claude and CI operate only on synthetic or de-identified data. Tools that process outside India (GitHub-hosted runners, Atlassian Cloud, Anthropic's processing of Claude) stay out of scope for localisation because they never hold regulated data. The rule the whole team internalises: no real customer data anywhere outside the India production estate, including as sample data in PRDs, design docs, tickets or test fixtures.

7Environments and data

Topology is the usual local, per-PR preview, staging, prod. The framework-relevant rules:

Environment config, schema and migrations all live as code in the repo, so Claude can reason over them and a schema change flags the data-model section of the relevant design doc through the same map.

Synthetic or de-identified data fills every environment Claude or CI touches. Real data lives only in production, behind the gate above. Preview and staging run on synthetic seed data, which is what makes them safe for an agentic team to operate freely.

The production estate sits in an India region on a MeitY-empanelled CSP, with its backups, disaster recovery, logs and encryption keys held in India, per the locked residency posture in section 6. Non-prod environments carry no regulated data and so are not bound by region.

8Ownership at a glance

  • PMs and designers own the product and design layer and the open decisions routed to them.
  • Engineers and architects own the technical design and code layers and the front-matter links on their artifacts.
  • Business, Compliance and Legal own the answers to the open decisions in their domain.
  • GitHub Actions orchestrates the deterministic pipeline; the publisher action owns the design-doc mirror; the bespoke linter owns map and coverage validation.
  • The Cowork judgment flow owns drift, decision and consistency detection and proposes fixes.
  • The framework steward owns the integrity pipeline, the Drift Register, the always-on Cowork machine, and triage disposition. This is the role that keeps the source of truth honest over time, which is the thing that quietly fails in every team that skips it.
