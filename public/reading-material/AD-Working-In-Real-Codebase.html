Working in a Real Codebase

The Three Skills That Turn Understanding Into Doing — Reading Code You Didn’t Write, Proving It With Tests, and Watching It Run

Primer 4 · The depth document — read it at the wall, not before

What this primer is, and how to use it

The first three primers gave you the map (how software moves), the parts (what it’s made of), and the engine (building with AI). This one is about the moves — the specific, repeatable things you do when you’re actually in a codebase trying to get something done. It’s deliberately more hands-on and less conceptual than the others.

Three skills live here, and they’re a single chain, not three separate topics. Something’s wrong, or you need to change something — so you read code you didn’t write to understand it. You make a change, and you prove it’s right with a test rather than hoping. Then it’s running for real users, and you watch it through observability to know it’s actually healthy. Debug → prove → watch. That’s the loop of real engineering work, and it’s what the task ladder will have you doing over and over.

Don’t read this cover-to-cover up front. Skim it once so you know what’s here, then come back to the exact section when you hit its wall — staring at unfamiliar code, trying to test something, or wondering why your deployed app is misbehaving. That just-in-time habit is how engineers actually learn this.

1 · Reading Code You Didn’t Write

This is the actual day-one skill of a Product Engineer, and almost nobody teaches it explicitly. You will spend far more time reading code than writing it — understanding what’s already there before you can safely change it, or figuring out why something behaves the way it does. Code you didn’t write (including code you wrote three weeks ago, or that AI wrote for you) is the normal condition, not the exception.

The beginner instinct is to read code like prose — top to bottom, every line, trying to hold it all in your head. That doesn’t work and isn’t how experienced engineers do it. They read with a question in mind and navigate toward the answer, ignoring everything irrelevant to it. The skill is targeted, not exhaustive.

The single most important reframe

You almost never need to understand a whole codebase. You need to understand the one path relevant to your task. “Where does the goal-progress percentage get calculated?” is answerable without reading 95% of the code. Hold a specific question, follow the thread to it, and let the rest stay a black box until a question makes it relevant. Trying to understand everything is the fastest way to understand nothing.

The techniques, concretely

Here’s how experienced engineers actually navigate an unfamiliar codebase. None of this is advanced — it’s just rarely said out loud.

  1. Start from something you can see, and work backwards

    You can see a number on a screen, a button, an error message. Those are your entry points. “This dashboard shows ‘68% to your goal’ — where does that come from?” Search the codebase for the visible text (“to your goal”), find where it’s rendered, and trace backwards from there toward the calculation. Visible thing → the code behind it is the most reliable way in.

  2. Follow the data, not the file structure

    Don’t try to map the folders. Pick a piece of data — the goal’s target amount — and follow its journey: where it’s entered, where it’s stored, where it’s read back, where it’s displayed. Following one piece of data through the system teaches you the architecture as a side effect, in the order that actually matters.

  3. Use search as your primary tool

    Your editor’s search-across-files (and “go to definition” / “find all references”) is how you navigate, not scrolling. Search for a function name to find everywhere it’s used. Search for a piece of text to find where it lives. Professional code reading is mostly search.

  4. Read the names, trust them provisionally

    Good code names things honestly: a function called calculateGoalProgress almost certainly does that. You can understand the shape of code by reading function and variable names alone, treating each as a labelled box you only open if you need what’s inside. This lets you skim at altitude and descend only where needed.

  5. Make the AI your tour guide

    This is the unfair advantage you have that engineers ten years ago didn’t. Paste a chunk of unfamiliar code into Claude and ask “explain what this does, step by step” or “where would I look to change how goal progress is calculated?” Point Claude Code at the whole repo and ask it to trace a path for you. But — and this is the Primer 3 distrust discipline applied to reading — verify its explanation against the actual code. It can misread too.

A worked example: tracing a bug

Let’s make this real. Suppose a user reports: “My savings goal says I’m 68% there, but I’ve saved ₹6.8 lakh of a ₹10 lakh goal — that should be 68%… wait, that’s right. But my other goal says 0% and I’ve definitely put money in.” You didn’t write this code. Here’s the trace.

The function you find by searching for “goal progress”
// goals.js — found by searching the codebase for "progress"
function calculateGoalProgress(goal) {
  const saved = goal.currentAmount;
  const target = goal.targetAmount;
  return Math.round((saved / target) * 100);1
}

// ...elsewhere, where a new goal is created:
function createGoal(name, target) {
  return {
    name: name,
    targetAmount: target,
    currentAmount: undefined2
  };
}
  • The math itself is correct: saved divided by target, times 100, rounded. So the calculation isn’t the bug — which means the inputs must be. This is the key move: when the logic looks right, suspect the data going into it.
  • There it is. A newly created goal sets currentAmount to undefined instead of 0. When you compute undefined / target, the result is NaN (“not a number”), and rounding that gives NaN, which the screen probably renders as 0% or a blank. The first goal worked because the user had added money (setting a real number); the second showed 0% because no money had been added since creation, so it was still undefined.

What just happened, and why it generalises

Notice the shape of that trace, because it’s the universal one. You started from a visible symptom (“says 0%”), searched for the relevant code, read the calculation and judged it correct, then reasoned backwards to the data feeding it and found the real cause upstream. You never read the whole app — you followed one thread from symptom to root. That’s debugging, and it’s 80% reading and reasoning, 20% changing. The fix here is one line (default to 0); finding it was the actual work.

Reading a stack trace: the error’s treasure map

When code crashes, it produces a stack trace — a wall of text that looks intimidating and is actually a precise map to the problem. It’s the chain of function calls that led to the crash, most-recent first. Learning to read one turns panic into a two-minute fix. Here’s the crash from the bug above, as it would appear:

A stack trace — read it top-down
TypeError: Cannot read properties of undefined (reading 'toFixed')1
    at formatProgress (goals.js:42:28)2
    at GoalCard (GoalCard.jsx:17:12)3
    at renderDashboard (Dashboard.jsx:88:4)
    at renderApp (index.js:23:1)4
    ... 14 more framework lines ...
  • The top line is what went wrong, in plain-ish terms: something tried to call .toFixed (a number-formatting function) on a value that was undefined. This is the same root cause as before, surfacing a different way — a missing number. The error type and message are the headline; read them first.
  • The first “at” line is where it went wrong, and it’s the one that matters most: file goals.js, line 42, column 28. This is your destination — open that file, go to that line. Nine times out of ten the fix is right there.
  • Each line below is the caller of the one above — the breadcrumb trail of how the code got there. GoalCard called formatProgress, the dashboard rendered the GoalCard. Useful for context, but you rarely need to go deep down the list.
  • The greyed lines are framework/library internals — code you didn’t write and won’t fix. Mentally skip them. A huge part of reading traces is knowing which lines are yours (your filenames) and ignoring the rest.

The move when you see a stack trace

Read the top line (what), jump to the first line that names your file (where), open it, and look. If it’s not obvious, paste the whole trace into Claude and ask “what is this telling me and where should I look?” — traces are exactly the kind of structured text AI reads well. The one thing you must not do is panic at the wall of text and close it. It’s a map, and X is usually on the second line.

When you’re staring at unfamiliar code — the move to make
You need to change something
Find the visible thing it affects (a label, a number, a button), search for that, and trace backwards to the code behind it.
Something is broken, no error shown
Start from the wrong output. Find where it’s calculated, confirm the logic, then suspect the data feeding it (as in the worked example).
Something crashed with an error
Read the stack trace top-down: what (top line), where (first line naming your file). Go there.
You’re lost in the structure
Stop mapping folders. Pick one piece of data and follow its journey through the system instead.
A chunk is genuinely opaque
Paste it into Claude: “explain step by step.” Then verify the explanation against the code — don’t take it on faith.
You’ve found the fix
Before changing anything, make sure you can explain the root cause out loud. If you can’t, you haven’t found it yet — you’ve found a symptom.

2 · Proving It Works: Testing as a Discipline

Primer 1 named the types of tests (unit, integration, E2E). This section is about actually thinking in tests — which is a different and more valuable thing. For a wealth platform where a calculation error is real money and a regulatory event, testing isn’t optional polish. It’s close to the centre of the job, and it’s the thing that lets you change code confidently instead of fearfully.

What a test actually is

Strip away the mystique: a test is just a small piece of code that runs your real code with a known input and checks the output is what you expected. That’s it. “When I call calculateGoalProgress with a goal that’s ₹5 lakh saved of ₹10 lakh, I expect 50.” If the code returns 50, the test passes (green). If it returns anything else, the test fails (red) and tells you. A test suite is hundreds of these tiny checks, run automatically in seconds.

Here’s what a real test looks like — the one that would have caught our bug from Section 1 before it ever reached a user:

A test for the goal-progress calculation
// goals.test.js — runs automatically in CI on every change
test("progress is 50% when half the goal is saved", () => {
  const goal = { currentAmount: 500000, targetAmount: 1000000 };
  expect(calculateGoalProgress(goal)).toBe(50);1
});

test("progress is 0% for a brand-new goal with nothing saved", () => {2
  const goal = createGoal("New car", 1000000);
  expect(calculateGoalProgress(goal)).toBe(0);3
});
  • The happy-path test: set up a known input (₹5 lakh of ₹10 lakh), call the real function, and assert (expect) the answer is exactly 50. Readable almost as English. This is the entire mechanic of testing.
  • The second test is the one that matters — it tests the edge case that actually broke. A brand-new goal, nothing saved yet. This is where your PM instinct for edge cases becomes a testing superpower: you naturally think “but what about when…”, and each “what about” is a test worth writing.
  • This test would have failed on the buggy code — createGoal set currentAmount to undefined, so the function returned NaN, not 0. Red test, caught in CI, never ships. That’s the whole value proposition: the bug is found by a robot in seconds, not by a customer in production.

Why “write the test first” changes how you think

You’ll hear engineers talk about writing the test before the code. It sounds backwards, but there’s a deep reason: writing the test first forces you to define exactly what “correct” means before you build anything. You can’t write expect(...).toBe(50) until you’ve decided, precisely, what the right answer is. That act of specifying the expected behaviour up front is identical to writing a crisp acceptance criterion — which is something you already do as a PM. Testing isn’t a new muscle so much as your existing spec-writing muscle, pointed at code.

What makes a test good (and what makes one useless)

A good test…A weak or harmful test…
Tests behaviour a user cares about (“progress shows correctly”).Tests trivial implementation details that don’t matter and break on any change.
Covers the edge cases — zero, empty, negative, huge, concurrent.Only tests the happy path, giving false confidence.
Is readable — you can see what’s expected and why.Is so convoluted that a failure tells you nothing.
Fails reliably when the thing it checks is broken.Is “flaky” — passes and fails randomly, so everyone learns to ignore it.

Flaky tests are worse than no tests

A test that passes and fails at random — usually because it depends on timing, network, or order — is genuinely harmful. Teams learn to ignore red from a flaky test, and then ignore a real failure hiding among the noise. If you write or inherit a flaky test, fixing or deleting it is real work, not housekeeping. “Green” only means something if red is always meaningful.

Reading a failing test

Most of your test interaction won’t be writing them — it’ll be reading one that just went red and figuring out why. A good test failure is a precise bug report. Here’s what one looks like:

A failing test — the output tells you everything
✗ FAIL  goals.test.js
  progress is 0% for a brand-new goal with nothing saved

    expect(received).toBe(expected)

    Expected: 01
    Received: NaN2

      at goals.test.js:9:423

Tests: 1 failed, 14 passed, 15 total4
  • What you said should happen: the answer should be 0.
  • What actually happened: the code produced NaN. The gap between Expected and Received is the bug, stated precisely. You don’t have to guess — the test hands you both numbers.
  • Exactly which test, and which line, so you can go straight to it. Same “where” skill as reading a stack trace.
  • The summary: 1 failed, 14 passed. The other 14 still work — so whatever you changed broke this one specific thing, narrowing the search enormously. This is why a good test suite makes changing code safe: it tells you instantly and specifically when you’ve broken something.
Testing — the move to make
You’re about to change code
Run the existing tests first, so you know the baseline is green before you touch anything.
You’re building something new
Ask: what would prove this is right? Write that as a test — ideally before or alongside the code, not after.
A test just went red
Read Expected vs. Received. The gap is the bug. Then decide: is the code wrong, or is the test wrong? Both happen.
You found a bug in production
Write a test that reproduces it (goes red), then fix the code (test goes green). Now it can never silently return.
You’re directing AI to build
Ask it for the tests too — “write tests including edge cases” — then read them critically. AI writing its own happy-path-only tests is a classic blind spot.
A test is flaky
Don’t ignore it. Fix the cause or delete it. A test no one trusts is worse than no test.

3 · Watching It Run: Observability

Tests prove your code is right before it ships. Observability is how you know it’s healthy after — once it’s running for real users, with real data, at real scale, where things happen that no test anticipated. If testing is the dress rehearsal, observability is watching the live show with the house lights up. It’s the difference between “it worked when I tried it” and “it’s working right now for everyone.”

The three things you watch (the classic trio)

Logs — timestamped messages the code writes as it runs (“goal created for user 4821”, “payment failed: card declined”). The detailed diary. Great for “what exactly happened to this request?”

Metrics — numbers measured over time (requests per minute, average response time, error rate, signups today). The dashboard gauges. Great for “is the system healthy overall, and is it trending wrong?”

Traces — the path of a single request as it moves through all the pieces of the system, with timing at each step. Great for “this was slow — which part was slow?”

Telling “slow” from “broken” — the core literacy

The single most useful observability skill for a Product Engineer isn’t running the tools — it’s reading them well enough to tell the difference between slow, broken, and fine. Those three call for completely different responses, and confusing them is how incidents get mishandled. Here’s a metrics view of an app and how to read it:

A metrics dashboard — what’s it telling you?
Goal Service — last 60 minutes

  Requests/min      1,240   (normal: ~1,200)      ● healthy1
  Error rate        8.4%    (normal: <0.5%)      ● ALERT2
  Avg response time 2,800ms  (normal: ~180ms)    ● degraded3
  Database          connected                          ● healthy

  Recent errors (from logs):
  14:32:09  TimeoutError: payment-gateway did not respond4
  14:32:04  TimeoutError: payment-gateway did not respond
  14:31:58  TimeoutError: payment-gateway did not respond
  • Traffic is normal — about the usual number of requests. So this isn’t a traffic spike or an outage where users can’t reach you. People are getting in fine.
  • But 8.4% of requests are erroring, against a normal of under half a percent. That’s the alarm. Roughly one in twelve users is hitting a failure right now. This is “broken,” not “slow.”
  • And responses are taking 2.8 seconds against a normal 180ms — fifteen times slower. So it’s also slow. Slow + erroring together is a strong signal that something the app depends on is failing and the app is waiting on it before giving up.
  • The logs confirm and pinpoint it: the payment gateway (a third party) is timing out. Your code isn’t broken — something it calls is. That completely changes the response: you’re not hunting a bug in your code, you’re handling a dependency failure (page the gateway vendor, show users a graceful “try again shortly”, maybe disable the payment path temporarily). Reading the signals correctly pointed you at the right problem in under a minute.

Why this is a product skill, not just an ops skill

Reading that dashboard told a product story: payments are failing for some users right now because a vendor is down, checkout feels broken, and you should communicate rather than debug. Knowing whether you’re looking at slow, broken, or fine — and whether it’s your code or a dependency — is exactly the judgement that lets a Product Engineer respond well to an incident instead of flailing. You don’t need to run Datadog or Grafana like an SRE; you need to read them like someone who understands what the numbers mean for users.

What an incident actually looks like

An “incident” is just: something is wrong in production and users are affected. The healthy response, which you saw foreshadowed in Primer 1’s rollback section, is a calm sequence, not heroics:

  1. Notice — ideally the monitoring tells you before customers do

    An alert fires (error rate crossed a threshold), or a metric goes red. Good observability means you find out from your dashboard, not from angry tweets. That’s the whole point of watching.

  2. Assess — how bad, how many, what’s the blast radius

    Read the signals: is it everyone or a slice? Slow or fully broken? Your code or a dependency? The dashboard above answers all three in a minute.

  3. Stop the bleeding — mitigate before you diagnose

    Roll back the recent deploy, flip off the feature flag, or disable the broken path. Get users to safety first; understand the root cause after. This is counterintuitive and correct.

  4. Diagnose and fix — calmly, now that no one’s actively bleeding

    With the pressure off, use the logs and traces to find root cause, write a test that reproduces it (Section 2), and ship the real fix.

  5. Learn — the blameless postmortem

    Afterwards, the team asks “what made this possible and how do we prevent the class of problem?” — not “whose fault.” The output is usually a new test, a new alert, or a new guardrail. Good teams get more reliable precisely because they treat incidents as lessons.

Observability — the move to make
Users report something’s wrong
Check the dashboard before diving into code. Is it slow, broken, or fine? Everyone or a few? That shapes everything.
Error rate is up but traffic is normal
Something’s failing, not overloaded. Check recent errors in the logs — and suspect a recent deploy or a failing dependency.
It’s slow but not erroring
Look at traces to find which step is slow. Often one dependency or one slow database query is the culprit.
Everything red, traffic at zero
Users can’t even reach you — an outage. Check the deploy host and whether the last deploy is the cause; consider rolling back.
You just shipped and metrics moved
Correlate with your deploy. If your change lines up with the regression, rolling back is the fast, safe first move.
It’s a dependency, not your code
Stop debugging your code. Handle it as a dependency failure: graceful degradation for users, and chase the vendor.

4 · The Loop, and How It Connects

Step back and see the three skills as the single loop they really are. They’re not three subjects to study — they’re three phases of every real change you’ll ever make to software.

Debug → prove → watch

Read (Section 1): something needs changing or fixing, so you navigate the existing code to understand it and find the right spot. This is where most of the time and thinking goes.

Prove (Section 2): you make the change and write a test that demonstrates it’s correct — especially on the edge cases — so a robot guards it forever and you can change things without fear.

Watch (Section 3): it ships, and you observe it running for real users, ready to read the signals and respond if reality surprises you, as reality does.

The worked example carried the whole loop without us naming it: a user reported a wrong percentage (a watch signal), you read the code to trace it to an undefined default, and the fix should land with a test that proves a new goal reads 0% — which, had it existed, would have caught the bug before any user ever saw it. That’s the loop closing on itself, each skill covering for the others.

The honest truth about this primer

You can’t absorb these three skills by reading about them — you absorb them by doing them, badly at first, on real code. This document’s job was to give you the moves so that when you’re staring at unfamiliar code, or a red test, or a dashboard full of alarms, you recognise the situation and know the first step. The fluency comes from the reps. The task ladder is where the reps live, and every one of them ends at the same gate: an engineer reads your work and decides whether it earns their respect. These three skills — reading, proving, watching — are most of what earns it.
