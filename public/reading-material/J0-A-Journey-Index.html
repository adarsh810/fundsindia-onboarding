What this document is

The index and drafting guide for the journey layer. Where the five entity references describe what things are and what states they can be in, the journey documents will describe how an investor actually moves through the platform: the canonical sequence of steps, the points where the path branches, and the ways it fails. This artefact does not draw any of those journeys. It catalogues them, decides the order to draft them in by mapping each to the open decisions blocking it, fixes the template every journey document will share, and gathers the decisions that drafting will force into the open. It is the analogue, for the journey layer, of the document index that earlier mapped the references and PRDs.

What it is not

Not a journey. No flow is drawn to completion here; the two small diagrams are a structural illustration and a template specimen, not journeys. Not a PRD and not a build plan. And not a fixed contract: the sequence and readiness below are a starting position that the first drafts will revise as they surface what is genuinely blocked.

Part I
Where the journey layer sits

1.The three layers

The journey layer is the connective tissue between the static entity model and the buildable feature specs. The references define the nouns and their states. The PRDs define what one feature must do. The journeys, in between, define how a whole flow runs end to end, which is exactly what neither neighbour captures on its own.

  R["References
entity and state ontology"] --> J["Journeys
governing end-to-end flows"]
  J --> P["PRDs

The arrows are decomposition. A PRD decomposes a slice of a journey into something the team can build; a journey draws on the entities and states the references own. The flow of authority runs the other way for ontology and the same way for sequence, which the next two principles make precise.

Key principle: the precedence rule

The reference owns the entity and its states. The journey owns the sequence and the transitions between those states. Neither silently overrides the other. When a journey needs a state or a transition the reference does not carry, that is a signal to update the reference, not to invent the state inside the journey and let the two drift. The journey is where gaps in the ontology are discovered; the reference is where they are fixed.

2.The altitude every journey holds to

A journey document is a governing view, not an exhaustive one. It draws three things and bullets a fourth. Getting this altitude right is what keeps the layer useful rather than a sprawl of flowcharts that go stale before the team arrives and over-constrain the product-engineers once they do.

  • The canonical spine, drawn. The happy path from start to finish, as a single clear flow.
  • The decision-point branches, drawn. Where the path genuinely forks, a persona that takes a different route, a rail that changes the steps, the decision and its branches are part of the spine.
  • The failure taxonomy, drawn or tabled. The canonical ways the journey breaks and how each is handled, because the exception paths are where the build is judged.
  • The special cases, bulleted. The rare, within-path edge conditions that change a value or add a check but not the sequence. These are listed as text, never drawn.

Special attention: the draw-or-bullet test

The line between a decision-point branch and a special case is the single judgment that keeps a journey document at the right altitude. The test: if it changes the path or the order of steps, draw it; if it only changes a value or adds a check on an existing step, bullet it. A persona divergence that reroutes the flow is a branch and belongs in the diagram. A rare condition that just adds a verification on a step already drawn is a special case and belongs in a bullet. Applied honestly, this keeps persona and rail divergence visible while killing the combinatorial sprawl.

3.Draft to surface decisions first, govern second

A drawn flow is a commitment to specific branches, and several of those branches depend on decisions still open in the reference registers. A journey cannot be governing while it rests on an unmade decision, because that bakes in exactly the rework the reference discipline was built to avoid. So the first pass of each journey is a decision-extraction tool. It draws the skeleton, lets the skeleton expose precisely which decisions it forces, and sends those to the business. Only once those are closed does the flow harden into something the team builds against. Pass one finds the questions; a later pass becomes the contract. Part V collects the questions the catalogue can already see coming.

Special attention: failure handling is not its own journey

There is deliberately no standalone "failure and reversal" journey. Per the altitude rule, failure is the third thing each journey draws for itself: every journey carries its own failure taxonomy, because how a redemption fails is not how onboarding fails. A single cross-cutting failure flow would either be too abstract to govern or would duplicate what each journey already owns. The order spine, J6, is the one shared exception, since its Failed and Reversed exits are inherited wholesale by every transaction that instantiates it.

Part IV
The journey-document template

Every journey document follows the same shape, so they read as a set and so the altitude holds by construction. Six sections, in this order.

SectionWhat it holds
1. The spineThe canonical happy path, drawn as a single flow. The start state, the end state, and the steps between.
2. Decision pointsEach genuine fork in the spine: the decision, the rule that decides it, and the branches. Drawn into or beside the spine.
3. Failure taxonomyThe canonical ways the journey breaks and how each is handled, mapped to the terminal states the relevant reference owns.
4. Special casesThe bulleted tail: rare, within-path conditions that change a value or add a check, never the sequence.
5. Entities and states exercisedThe references this journey draws on, and any state or transition it implies that a reference does not yet carry, flagged for propagation back per the precedence rule.
6. Decisions surfacedThe open decisions this journey's drafting forced into the open, each routed to an owner, feeding the register in Part V.

The notation

Journey spines are drawn in Mermaid, embedded in the same HTML house style as everything else. The choice is deliberate: Mermaid source is plain text, so a journey document is diff-able and version-controllable as it evolves with the team, and the diagram lives next to the prose that explains it rather than in a separate tool. A visual tool is fine for a presentation, but the source of truth stays here. The specimen below is the skeleton of J6, the order spine, drawn at the governing altitude: the happy path, the decision-driven exits, and nothing more.

flowchart TD
  A([Placed]) -->|pre-flight pass| B[RoutedToRail]
  A -->|pre-flight fail| F([Failed])
  B -->|rail accepts; money initiated| C[Acknowledged]
  B -->|payment or rail failure| F
  C -->|AMC or RTA accepts| D[Allotted]
  C -->|rejection| F
  D -->|money and units reconciled| S([Settled])
  D -->|dishonour or error| R([Reversed])

That is the whole altitude in one picture. The persona and rail branches would attach as decision points, the rejection causes would be enumerated in the failure taxonomy, and a rarity like a partial allotment would be a bulleted special case. The diagram never tries to hold all of it.

Key principle: this register is the point of the artefact

The catalogue and the sequence are useful, but the work that turns the journey layer from drawing into governing is closing these decisions. The ones blocking Wave 1, the rail choice and the Registered-status position, are the ones to take to the business now, before or alongside drawing J7. Everything else can be drawn decision-surfacing and hardened as its row clears.
