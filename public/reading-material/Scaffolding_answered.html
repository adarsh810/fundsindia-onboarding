Question

VCP and hosting: which platform, and cloud-hosted versus self-managed. Does any India data-residency or audit requirement constrain it?

Decision

Options & rationale

Options evaluated

GitHub, GitLab.

Trade-offs / rationale

A.2

Repo Topology

Locked

Question

Repo topology: monorepo, polyrepo, or hybrid, and the tooling that follows (Nx, Turborepo, Bazel). Decide it against the domain-service shape and the one-adapter-per-domain rule.

Decision

Monorepo, single-stack Java, Gradle multi-project build (no Nx/Bazel/Turborepo). Each service still builds and deploys independently (own Docker image, own K8s Deployment/pods) via path-filtered CI.

Options & rationale

Options evaluated

Monorepo, Polyrepo. build tools compared

Trade-offs / rationale

  • Cross-repo coordination: Polyrepo's real cost is contract/schema changes needing coordinated PRs across many repos — worst early, while domain boundaries are still moving. Monorepo removes this by construction: contracts live as one in-repo package, consumed directly.
  • Deployment stays decoupled from source layout: monorepo ≠ monolith — each service builds its own artifact and deploys to its own K8s Deployment/pods independently (own scaling, own rollback, own blast radius), triggered by path-filtered CI.
  • Polyglot ruled out: considered Java (domain services) + Node (I/O-bound adapters), but Java virtual threads (stable since Java 21) close most of Node's I/O-concurrency advantage, and polyglot would have doubled tooling/observability/security-scanning/on-call surface for a 10-person team. Staying single-stack also removes the need for Nx/Bazel entirely.
  • Tooling: Nx/Bazel/Turborepo mainly solve affected-graph builds, caching, task orchestration, and module-boundary enforcement. Gradle multi-project already provides the first three natively, and ArchUnit enforces the one-adapter-per-domain rule as a build-breaking test — no new tooling the team hasn't used.

A.5

Secret Hygiene at the Source

Locked

Question

Secret hygiene at the source: pre-commit and CI secret scanning, so a credential never enters history.

Decision

GitHub push protection + secret scanning (org-wide, blocking mode), included in the Enterprise Cloud tier. Custom secret patterns defined for every vendor integration. Mandatory credential rotation on any detected leak.

Options & rationale

Options evaluated

Push protection (blocking) vs. scan-after-the-fact (alerting); mandated pre-commit hook vs. none.

Trade-offs / rationale

  • Push protection blocks the push itself, so a secret never enters shared history — scan-after-the-fact only alerts once it's already there, and history can't be reliably scrubbed in a distributed VCS.
  • Generic secret-scanning patterns won't recognize vendor-specific credential formats (FP/Cybrilla, Razorpay, HyperVerge, AA provider, and any future vendor) — custom patterns needed per vendor, added as each is onboarded.
  • Pre-commit hook is bypassable (--no-verify) and adds ongoing maintenance overhead (tooling install, entropy-based false positives) for a 10-person team; push protection already covers the risk that matters. Left as individual opt-in, not mandated.
  • Detection is not remediation: any leak found by any layer triggers mandatory rotation of that credential, logged as an audit event (item E).

CI/CD & Release

Lock early
B.1

CI Platform & Pipeline Stages

Locked

Question

CI platform and the standard pipeline stages: build, lint, typecheck, unit, integration, security scan, artifact.

Decision

GitHub Actions (follows from A.1). Stages: Build → Lint (Checkstyle + SpotBugs) → Unit (JUnit 5 + ArchUnit) → Integration (Testcontainers + WireMock/vendor sandboxes) → Security scan (CodeQL SAST + dependency/SCA scan + OWASP ZAP DAST, scheduled against staging) → Artifact (Docker image → GitHub Container Registry). No separate Typecheck stage — Java's compiler folds this into Build. Runners: GitHub-hosted for the included 50k min/month, and GitHub-hosted overage billing to start; self-hosted runners deferred until overage cost justifies the setup.

Options & rationale

Options evaluated

Checkstyle+SpotBugs vs. PMD (lint); GitHub-hosted overage vs. self-hosted runners (ARC on the K8s cluster) vs. third-party runner vendors.

Trade-offs / rationale

  • Checkstyle (style) and SpotBugs (bug patterns) are complementary, not redundant — most Java shops run both.
  • OWASP ZAP is free, open-source, and has a native GitHub Action — closes the DAST gap flagged in A.1 without a new vendor bill.
  • Third-party runner vendors (BuildJet, etc.) are cheaper than GitHub's overage rate but route source code and short-lived cloud credentials through a new external vendor — a real risk surface for a regulated platform. Ruled out.
  • Self-hosted runners via GitHub's Actions Runner Controller (ARC) on the existing K8s cluster would be cheaper still and avoid that exposure, but add operational setup. Deferred rather than adopted day one — start with GitHub-hosted runners (including paying overage), revisit self-hosted once actual overage spend justifies the investment.
B.2

Artifact Strategy

Locked

Question

Artifact strategy: immutable, versioned artifacts in a registry, with the same artifact promoted across environments rather than rebuilt per environment.

Decision

Build once, promote everywhere. Docker images tagged immutably by commit SHA, with an additional semantic-version tag on release builds. Stored in GitHub Container Registry (carries forward from B.1). Retention: keep everything currently deployed to any environment, plus 30 days of history for superseded images, prune the rest. No rebuild per environment — only configuration changes across dev/staging/prod (item I), the binary never does.

Options & rationale

Options evaluated

Build-once-promote vs. rebuild-per-environment.

Trade-offs / rationale

  • Rebuilding per environment can silently pull a different base-image patch level or resolve a dependency differently than what was tested in staging — reintroduces the "worked in staging, broke in prod" class of bug that immutable promoted artifacts exist to eliminate.
  • SHA tag gives traceability; semver tag on release builds gives a human-readable reference for incidents, release notes, and audit conversations about what's running in prod.

Question

Infrastructure as code and provisioning: Terraform or Pulumi, and GitOps for deploys if you land on Kubernetes.

Decision

  • K8s deployment: Kubernetes, Helm for per-environment templating (values-dev/staging/prod.yaml), ArgoCD for GitOps (pull-based reconciliation from the monorepo's /infra/helm path — CI never holds cluster credentials, its last step is a PR bumping an image tag). Promotion gated by both the PR review (A.4) and ArgoCD's sync policy (auto vs. manual per service — sensitive services like the ledger require manual sync as a second, deliberate gate separate from code review). ArgoCD topology (single instance + Projects/RBAC vs. separate instance per environment) to be finalized during infra setup.
Options & rationale

Options evaluated

Terraform vs. Pulumi; GitHub Actions vs. a dedicated Terraform automation platform; Helm vs. Kustomize; GitOps (ArgoCD) vs. CI pushing directly to the cluster; AWS vs. GCP (leaning AWS on BAU-org precedent, mirroring N.4's reuse-of-existing-tooling logic — pending final confirmation).

Trade-offs / rationale

  • Terraform's ecosystem/hiring advantage (every DevOps hire already knows it, cloud providers document it first) outweighs Pulumi's Java-language affinity for a lean team; runs as a lightweight CI job, no new hardware or platform.
  • AWS lean follows the same logic as N.4 (Jira/Confluence): reusing infra the BAU org already operates lowers onboarding friction and avoids standing up parallel cloud-vendor relationships/billing/support — kept as a lean rather than a full lock since, unlike project-tracking tooling, cloud provider has deep, hard-to-reverse downstream implications (every "provider TBD" item elsewhere in this checklist) that warrant a deliberate confirmation rather than a one-line decision.
  • Helm's chart ecosystem (reusable third-party charts for Prometheus, cert-manager, ArgoCD itself) plus built-in release/rollback tracking outweighs Kustomize's simplicity for a team new to K8s tooling.
  • GitOps (ArgoCD) over direct CI push: promotion becomes a reviewed PR with an audit trail via git history, and CI never holds cluster credentials — a real security improvement for money-movement infra, directly satisfying this item's "auditable deploys and segregation of duties" language.
  • Kubernetes' built-in DNS-based service discovery (Service + CoreDNS + kube-proxy/CNI) replaces the need for a separate discovery tool (e.g. Eureka/Consul) entirely.
  • Full infra deep-dive and setup scheduled for the week before the team's mid-August arrival.
B.4

Deployment & Rollback Strategy

Locked

Question

Deployment and rollback strategy: blue-green, canary, or rolling, and how a bad deploy on a money-movement service is detected and reverted fast.

Decision

Canary (via Argo Rollouts), applied uniformly across all services — no tiering by service sensitivity. Before Prometheus/SLO metrics exist (item D), canary runs as a staged traffic-percentage rollout with fixed timed pauses (no automated analysis gate). Once item D is decided, the same Rollout definitions gain an analysis step for automated promote/abort based on real metrics — no tooling migration needed later. Every service also ships behind a feature flag as an independent safety layer (tooling deferred to B.5).

Options & rationale

Options evaluated

Uniform canary vs. tiered strategy (canary for critical services, rolling update for the rest); canary vs. blue-green.

Trade-offs / rationale

  • Uniform strategy trades a small amount of "extra setup for low-stakes services" for one consistent deployment behavior to reason about everywhere — especially valuable during an incident, when recalling which strategy a given service uses shouldn't be part of the cognitive load.
  • Canary is the strongest fit for this item's own framing ("detected and reverted fast") — a bad deploy is caught at a small percentage of real traffic before most transactions touch it. Blue-green gives fast reversal but weaker detection (found out only after 100% traffic cutover) and costs 2x capacity during the switch — ruled out.
  • Feature flags are a complementary, not redundant, layer: canary/metrics catch a bad deploy, but a flag lets you disable specific functionality instantly with no deployment at all.
B.5

Database Migration Discipline

Locked

Question

Database migration discipline in the pipeline, with special care for the bitemporal ledger and entity store: forward-safe, reversible, tested before prod.

Decision

Flyway. Schema changes are versioned SQL files in the monorepo, reviewed via the same PR process as code (A.4); the same Flyway engine and the same versioned files are applied to dev/staging/prod (build-once-promote-everywhere applied to schema, mirroring B.2). All migrations follow expand-contract: additive-only changes compatible with both old and new app code, with destructive cleanup (dropping the old column/table) as a separate, later migration — never a rename/drop/type-change in one step. "Reversible" means the application can roll back to the previous version without needing a database rollback, not a tested DOWN script per migration. Ledger schema migrations never touch existing data rows and route through the same stricter CODEOWNERS review as other ledger changes (A.4). Migrations run as their own separate ArgoCD Application (manual sync policy), fully decoupled from each service's own deployment Application — applied explicitly, during an off-hours window, by an engineer manually triggering the sync, not automatically as part of any deploy. Tested via Testcontainers in the integration stage (B.1, apply-from-zero) and against staging with synthetic data (item C) before prod.

Options & rationale

Options evaluated

Flyway vs. Liquibase; migration coupled to deploy (ArgoCD PreSync hook) vs. decoupled (separate manually-synced Application); DOWN-script reversibility vs. expand-contract-as-reversibility.

Trade-offs / rationale

  • Flyway's simpler versioned-SQL model fits the Java/Gradle stack better than Liquibase's heavier changeset format, whose extra power (multi-database abstraction, automatic rollback generation) isn't needed on one database engine.
  • Expand-contract is required by canary (B.4): multiple app versions run against the same database simultaneously during a rollout, so a migration must stay compatible with both for the duration.
  • Decoupling migration timing from deploy timing is safe precisely because expand-contract already guarantees compatibility — the only ordering rule is "migrate before the app version that needs it ships," not "at the same instant." Off-hours, manual execution limits the blast radius of migrations that lock or scan large tables, even when the change itself is logically safe.
  • Migrations still run as an in-cluster Job with cluster-local database credentials, not from GitHub Actions — consistent with the "CI never holds live prod credentials" principle already applied to GitOps (B.3).

Feature Flags to Decouple Deploy from Release

Question

Decouple deploy from release with feature flags, so the two-UI-constrained experience can ship dark and flip when ready.

Decision

Unleash, self-hosted on the existing K8s cluster (own Helm chart, own ArgoCD Application, same pattern as every other service). Native Unleash Java SDK used directly — OpenFeature abstraction layer considered and deferred (see rationale). Flags evaluated server-side in the BFF/domain services, not independently in each UI; the BFF exposes only resolved flag state to the two frontends.

Options & rationale

Options evaluated

Unleash vs. Flagsmith vs. GrowthBook vs. LaunchDarkly vs. homegrown; native Unleash SDK vs. OpenFeature abstraction with Unleash as the backing provider.

Trade-offs / rationale

  • Open-source, self-hosted, free Community edition with unlimited users/projects/environments — no new recurring per-seat SaaS vendor, reuses infra already operated (B.3), consistent with the "open source now, build/upgrade later if required" approach applied elsewhere in this checklist.

  • Local flag evaluation by default (Java SDK polls every 15s, caches in-memory, persists a local backup file) — no network call per flag check, and evaluation keeps working on last-known state even if the Unleash server itself is unreachable. Flagsmith's default server-side evaluation is API-call-based, a weaker fit for latency/resilience-sensitive services (item K).
  • GrowthBook ruled out — oriented toward growth/experimentation (A/B testing, warehouse-connected metrics) rather than the governance-first need here. LaunchDarkly ruled out on recurring per-seat cost that scales against a 10→50 person team.
  • OpenFeature (CNCF Incubating, production-ready) would reduce future vendor lock-in by abstracting the flag-check API from Unleash specifically, but the available Unleash provider for it appears community-maintained by an individual, not the official Unleash org — deferred pending a maintenance-health check, rather than adopted on faith alongside the Unleash decision itself.
  • Flag updates require no redeploy — picked up by every running instance within the 15s poll interval, which is the entire point of this checklist item.

Change Control for Production

Locked

Question

Change control for production: auditable deploys and segregation of duties that satisfy a regulated audit without strangling velocity.

Decision

Largely a synthesis of prior decisions, plus one new rule. Auditable deploys: every prod-bound change (code, infra, schema, flags) is a reviewed PR — git history is the audit trail (A.4, B.3, B.5, B.6) — backed by signed commits, CODEOWNERS routing, ArgoCD sync history, and Unleash's audit log as independent records of what was actually deployed. Everywhere else, one approval + automated promotion stands unchanged. Repo admins retain bypass ability for emergencies, via the audited allowlist already established in A.4 — GitHub logs any bypass as a distinct audit event. No separate formal change-ticket system added on top of the PR.

NA

C.1

Environment Topology

Locked

Question

Environment topology: local, dev, integration, staging or UAT, production. Define how many and the job of each, with staging kept prod-like.

Decision

Four tiers, not five — dev and integration merged into one. Local (laptop, docker-compose, mocked/stubbed vendor adapters), Dev (shared, continuously deployed on every merge to main, integrates against real vendor sandboxes, expected instability), Staging/UAT (prod-like, manually promoted, the final gate — DAST scans and migration testing with synthetic data run here), Production. Cluster topology: hybrid — one shared K8s cluster for Dev + Staging (namespace-per-environment), a fully separate, isolated cluster for Production. This also resolves B.3's deferred ArgoCD question: Production gets its own ArgoCD instance; Dev/Staging share one ArgoCD instance with Projects/RBAC distinguishing them.

Options & rationale

Options evaluated

Four tiers (dev+integration merged) vs. five (kept separate); cluster topology — separate cluster per environment vs. one shared cluster (namespace-per-environment) vs. hybrid.

Trade-offs / rationale

  • Dev and integration do the same job in practice — merged code running somewhere shared, integrating against real vendor sandboxes — keeping them separate would mean two more environments to keep prod-like-enough for a 10→50 person team, for little added value.
  • Hybrid cluster topology applies extra isolation only where the stakes are highest (production, real money/PII), matching the pattern used throughout this checklist, while Dev/Staging (synthetic data only) share infrastructure to keep cost and operational overhead down.
  • "Staging kept prod-like" means same Helm charts, same K8s version, same vendor-integration shape — only sizing values differ — so load-test (item G) and canary signals from staging are trustworthy, not staging-only artifacts.
C.2

Rail Sandboxes

Locked

Question

Rail sandboxes: how each vendor (FP/Cybrilla, Razorpay, HyperVerge, the AA provider) is exercised in lower environments without real money, and the fallback where a vendor offers no sandbox.

Decision

Sandbox-first per vendor; WireMock as the confirmed fallback and supplementary tool (already selected in B.1, no new tooling). WireMock runs in two modes: ephemeral via Testcontainers for CI (B.1), and a standing deployed instance in Dev (C.1) for other services to call through the adapter when no usable sandbox exists. WireMock is also used deliberately for failure-injection (timeouts, malformed responses, error codes) even where a vendor sandbox exists, since sandboxes typically only demonstrate the happy path and can't simulate degradation needed for resilience testing (item K). Stubs are contract-driven, validated against each vendor's actual published API contract rather than hand-typed (ties to item G's contract testing). Actual sandbox availability per vendor (FP/Cybrilla, HyperVerge, AA provider) is unconfirmed and being verified directly with each vendor — Razorpay's test mode is the one confirmed-mature sandbox among the four. This item to be revisited once vendor conversations conclude.

Options & rationale

Options evaluated

Sandbox-only vs. sandbox-first-with-mock-fallback vs. mock-only.

Trade-offs / rationale

  • Sandbox-first with a mock fallback gets real-vendor-behavior fidelity where available while not blocking development on vendors that lack one.
  • Reusing WireMock (already decided in B.1) rather than adopting a separate mocking tool avoids new tooling for a role that's really an extension of an existing decision.
  • Mocks earn a permanent role beyond fallback: no vendor sandbox reliably simulates failure modes on demand, so failure-injection testing needs WireMock regardless of sandbox quality.
  • Per-vendor sandbox confirmation is genuinely unknown at decision time (vendor/contract-specific, not something to assume) — left as an explicit open action item tied to ongoing vendor conversations, not silently assumed either way.

Test Data

Revisit
⚑ Revisit

Identifier-format specifics (synthetic PAN/Aadhaar-linked test values) depend on the same vendor sandbox conversations flagged as open in C.2. Revisit this item once those conclude.

Question

Test data: synthetic, PII-safe datasets, since real personal data cannot sit in lower environments under DPDP. Define seeding and refresh.

Decision

Pure synthetic generation only — never anonymized/masked production data. DataFaker for realistic-but-fake PII, generation logic in libs/common-testing (shared with integration tests, B.1). Synthetic datasets deliberately include known-bad/edge-case records (KYC-rejected investor, an injected reconciliation break), not just happy-path data.

Options & rationale

Options evaluated

Synthetic generation vs. anonymized/masked production data.

Trade-offs / rationale

  • Anonymized production data always carries residual re-identification risk (real-world re-identification via auxiliary field correlation is a documented failure mode) — pure synthetic generation is a categorically stronger DPDP guarantee since no real person's data is ever involved, not just well-scrubbed.
  • Flyway is the right tool for small idempotent reference data (matches B.5's existing tooling) but the wrong tool for bulk-volume generation, which is a different operation at a different scale.
  • Dev's nightly reseed matches its designed instability (C.1); Staging's on-demand-only refresh avoids disrupting in-progress UAT walkthroughs.
  • Deliberately-injected bad/edge-case records exist so item G's reconciliation harness has real failure scenarios to detect, not only idealized data.
C.5

Environment Access & Break-Glass

Revisit
⚑ Revisit

Kept deliberately simple for now — the detailed break-glass mechanism (bastion pattern, temporary IAM credential specifics, audit logging configuration) is not fully designed and should be revisited before go-live.

Question

Environment access: who can reach production, by what path, with a break-glass procedure.

Decision

All human access to production is read-only, with no exception. Any write or correction — including ledger corrections — happens exclusively through application-level workflows: existing APIs, or new purpose-built workflow tooling composed from existing APIs to address a specific problem. Direct manual writes (DB edits, resource edits) are prohibited outright, not merely gated behind approval. Day-to-day debugging happens through observability (logs/traces/metrics, items D/E) as the primary interface, not direct access.

Options & rationale

Options evaluated

Break-glass elevated write access (time-boxed, approved) vs. read-only-always with all writes routed through application workflows.

Trade-offs / rationale

  • Routing every write through existing or purpose-built workflow APIs guarantees the same consistency and relationship integrity the application already enforces elsewhere — e.g., a profile update can't happen without its corresponding log/history entry, because both happen inside the same code path, not as two separately-remembered manual steps.
  • This removes the highest-risk category (manual data surgery, especially on the ledger) from the access-control problem entirely, rather than gating it behind approval — a simpler and stronger guarantee than a well-governed break-glass-write process.
  • Read-only-always also simplifies what needs auditing: viewing is lower-stakes than writing, and the harder mechanism design (bastion pattern, temporary credentials, write-path audit logging) is deferred rather than built prematurely for a capability that no longer needs to exist.

D.1

OpenTelemetry Standardization

Locked

Question

Standardise on OpenTelemetry early, so instrumentation is not redone service by service.

Decision

OpenTelemetry adopted as the standard instrumentation layer for all signals (traces, metrics, logs). Java auto-instrumentation agent (bytecode instrumentation, in-process) covers common frameworks (Spring, JDBC, HTTP clients, Kafka); manual spans added only for business-specific operations (e.g. reconciliation cycle). All services push telemetry via OTLP to a shared, per-cluster OTel Collector (one per cluster, matching C.1's hybrid topology). Backend/observability vendor deliberately deferred — the Collector's export config is the only thing that changes when that's picked, not app instrumentation.

Options & rationale

Options evaluated

OpenTelemetry (full adoption) vs. vendor-native APM agent (Datadog/New Relic/Dynatrace) vs. hybrid Micrometer (metrics) + OTel (traces).

Trade-offs / rationale

  • OTel decouples instrumentation from backend choice via OTLP + Collector — important since both cloud provider (B.3) and observability backend are still undecided; avoids re-instrumenting every service later.
  • Java auto-instrumentation agent covers the common path (Spring, JDBC, Kafka, HTTP) with zero code changes via bytecode instrumentation; manual spans reserved for business-meaningful operations the agent can't infer.
  • Vendor-native APM agents offer less setup friction but lock instrumentation to that vendor's backend — ruled out while backend choice is still open.

PII in Logs

Revisit
⚑ Revisit

Question

Decision

Three layered controls, not one:

  1. Tokenization at the DB layer — most tables reference PII (PAN, Aadhaar-linked values) by token, not raw value, via DB normalization; the raw value lives only in a narrow, access-controlled vault table/service. Options & rationale

Options evaluated

Downstream-only redaction (Elastic pipeline as the sole control) vs. layered structural prevention (tokenization + code-level backstop + Elastic backstop).

Trade-offs / rationale

  • Layering means no single control is a point of failure — tokenization prevents most PII from reaching log-adjacent code at all; the other two layers exist specifically to catch what the layer before it misses, not to duplicate it.

  • Raw-field encryption (the vault table's own at-rest protection) is deferred by design — the decision to tokenize is locked now, but the encryption mechanics (KMS envelope encryption, key custody, rotation cadence) don't need to be finalized to lock this item.

K.5

Service Communication Protocol & Contract Enforcement

Locked

Question

Decision

Options & rationale

Trade-offs / rationale

  • Request volume doesn't justify gRPC's performance case yet — projected platform volume (~150M internal service-hops/day at 1M DAU, per earlier modeling) isn't large enough for JSON-over-HTTP to be a real bottleneck; gRPC's binary/HTTP2 performance edge is real in general but not load-bearing here.
  • Avoids introducing a second protocol/toolchain (Protobuf syntax, codegen pipeline, grpcurl-based debugging) for a 10-person team — one protocol, one debugging model (curl/Postman/browser devtools) for every call, internal or external.
  • Contract enforcement isn't given up by choosing REST — it's a deliberate build-order discipline, not "write REST and hope": spec-first OpenAPI with generated server interfaces gets a comparable guarantee to gRPC's compile-time contract, provided codegen is actually wired into CI as a checked step. Code-first (spec generated from annotations) would have quietly failed to deliver the enforcement being asked for, since the code would remain the source of truth either way.
  • Revisit gRPC later if a concrete performance or streaming need actually emerges — same "start simple, upgrade later if required" pattern used elsewhere in this checklist (Vault, OpenFeature, self-hosted runners).
  • Tooling: OpenAPI Generator (or springdoc's client/interface generation mode, used spec-first not code-first) for the Java/Spring Boot stack — same monorepo-contract-package structure question as A.6 applies to where the .yaml specs themselves live.

L.1

Capacity Assumptions & Autoscaling Approach

Locked

Question

Capacity assumptions and an autoscaling approach.

Decision

HPA (Horizontal Pod Autoscaler) for pod-layer horizontal scaling — conservative thresholds and min-replica floors (earlier scale-up triggers, longer scale-down cooldowns to avoid flapping) — deployed declaratively via the existing Helm/ArgoCD GitOps pipeline (B.3), same as any other manifest. Options & rationale

Options evaluated

L.2

Async, Event-Driven Processing

Locked

Question

Async, event-driven processing for throughput where a synchronous path is not needed. (Reframed during discussion — see rationale.)

Decision

Synchronous is the default — most user-facing flows (view portfolio, submit an order intent, check KYC status) return a direct response, since the user is waiting on screen for an outcome. Event-driven, at-least-once processing is a deliberate carve-out for two categories: (1) external data-fetch flows that are inherently slow/batchy and don't require blocking the user — e.g. fetching folios/investments from the RTA, triggered on a schedule or on-demand, landing via an event that updates a read model, UI shows last-synced state rather than blocking; (2) vendor calls that are non-blocking by the vendor's own design — e.g. payment aggregator collection for a lumpsum investment, where initiating payment is synchronous (user needs the redirect link immediately) but completion arrives via webhook, treated as an inbound event triggering order confirmation/ledger entry/notification. Both carve-out categories require: idempotent consumers (K.2's idempotency-key pattern, since at-least-once delivery means redelivery is expected, not exceptional) and key-based partitioning/ordering (e.g. by folio ID or order ID) so events for the same entity process in order while different entities process in parallel.

Options & rationale

Options evaluated

NA — reframing of the original statement's default, not a multi-option choice.

Trade-offs / rationale

  • The original checklist framing ("async where sync isn't needed," "for throughput") was circular (no actual test for when sync is needed) and understated the real motivation — the domain event spine (referenced elsewhere, e.g. D.4) is architectural, not primarily a throughput optimization — and omitted the real costs (eventual consistency, harder tracing across an async boundary, delivery/ordering semantics).
  • Flipping the default (sync unless a concrete carve-out applies) matches how money-movement platforms should reason about consistency — synchronous confirmation is the safe default for user-facing outcomes; async is opted into for specific, justified reasons (RTA latency variability, a vendor's own async completion model), not assumed globally "for throughput."
  • Idempotency (K.2) and key-based ordering are named explicitly here because at-least-once delivery without them is exactly how a payment webhook redelivery could double-book a ledger entry — not a theoretical risk, the direct failure mode this carve-out creates if unaddressed.
